## 0. 전제 하나

이 문서는 "학습용 도구"를 정의한다. 그런데 이 도구를 만드는 과정 자체가 이 도구로 배우려는 내용(DOM, 이벤트, 상태 관리, 모듈 설계)의 실전판이다. 도구 완성이 목표가 아니라 **도구를 만들면서 T1~T2를 통과하고, 완성된 도구로 T3~T4를 통과하는 것**이 실제 시나리오다. 스코프 판단은 전부 이 기준으로 한다.

## 1. 문제 정의

### 1.1 현재 상황

13년 커머스 경력 후 웹퍼블리싱으로 전환. HTML/CSS는 대규모 프로젝트 2건(392p, 164p)으로 검증된 상태. 그러나 JS/React는 다음 지점에서 막힌다.

| 구분 | 현재 | 목표 |
|---|---|---|
| HTML/CSS | 대규모 실전 경험 | 유지 |
| JS | 코드를 읽을 수는 있음 | 백지에서 작성 |
| React | 개념만 인지 | 마크업을 컴포넌트로 분해 |

### 1.2 기존 학습 수단의 한계

| 수단 | 한계 |
|---|---|
| 강의/책 | 예제가 남의 코드다. 내 마크업과 연결되지 않는다 |
| CodePen·CodeSandbox | 자유도는 높지만 커리큘럼이 없다. 뭘 해야 할지가 없다 |
| 온라인 코딩 문제 | 알고리즘 중심. 퍼블리셔가 실무에서 쓰는 DOM/이벤트/상태와 무관 |
| 프로젝트 클론 | 난이도 점프가 크다. 중간 단계가 비어 있다 |

**핵심 결핍: "내가 이미 만든 마크업"을 교재로 쓰는 학습 경로가 없다.**

### 1.3 제품 가설

정적 사이트 한 페이지 안에서 (1) 문제 제시 (2) 코드 작성 (3) 즉시 실행 (4) 자동 검증이 한 화면에 붙어 있고, 교재가 **JW Anderson·HOOT UP의 실제 마크업**이면, 퍼블리싱 → JS → React 전환의 심리적·기술적 간극이 줄어든다.

## 2. 사용자

### 2.1 유일 페르소나

- 43세, 웹퍼블리셔 전환 중, 구직 활동 병행
- CSS 아키텍처(토큰, `:is()` 압축, 시맨틱 알리아스)에는 강함
- 접근성·문서화에 대한 기준이 높음 → 도구 자체도 그 기준을 만족해야 사용을 지속함
- 학습 시간은 구직 활동 사이의 파편 시간 → **한 세션 15~25분 안에 한 단계가 끝나야 함**

**JS 문법 지식은 백지에 가깝다.** 변수·`console.log`·함수가 각각 무엇인지 정확히 설명하지 못하는 상태에서 시작한다. 코드를 읽으면 대강 무슨 일이 일어나는지는 짐작하지만, 빈 화면에서 한 줄을 쓰지는 못한다.

> **정정 이력 (v0.4)** — 초판은 "CSS 아키텍처에 강함 → 추상화·구조화 사고는 이미 있다"고 적었다. **이 추론은 틀렸다.** CSS 설계 역량과 JS 문법 지식은 별개다. 이 오류가 레슨 설계에 그대로 옮겨져, 첫 레슨이 `typeof`·`Number()`·`String()`·`Number.isNaN()`을 한꺼번에 요구하는 형태가 됐다. 실제 사용자에게는 전부 처음 보는 단어다. 레슨 구조 재설계(T0 트랙 신설, 단계 분할)는 이 정정에서 나온 결과다.

## 3. 제품 정의

### 3.1 한 줄 정의

> 마크업을 이미 쓸 줄 아는 사람이, 그 마크업을 재료로 JS와 React를 손으로 익히는 정적 웹 플레이그라운드.

### 3.2 설계 원칙

1. **한 화면에서 끝난다** — 탭 이동, 페이지 이동 없음
2. **교재는 내 코드다** — 예제 마크업은 실제 포트폴리오에서 발췌
3. **틀린 걸 도구가 알려준다** — 눈으로 비교하지 않고 검증이 판정
4. **레슨은 데이터다** — 레슨 추가에 애플리케이션 코드 수정이 필요 없어야 한다
5. **도구가 학습을 방해하지 않는다** — 무한루프, 로딩 지연, 상태 소실은 학습 중단 사유다

### 3.3 명시적 비범위 (Out of Scope)

| npm 패키지 임의 설치 | 브라우저 번들러 필요. 비용 대비 학습 효과 낮음 |
| TypeScript | JS를 먼저 확보. v2 이후 |
| ~~다중 파일 프로젝트~~ | **비범위 해제.** T8로 이동하고 엔진 M4를 선행 조건으로 둔다. 근거는 §4 T8 |

## 4. 학습 트랙 구조

**트랙은 고정, 레슨 수는 고정하지 않는다.**

초판은 "트랙 4개 × 레슨 8개 = 총 32레슨 고정"을 스코프 방어선으로 삼았다. **이 방어선은 스코프가 아니라 밀도를 눌렀다.** 8개에 맞추려다 T1-1 하나가 `typeof`·`Number()`·`String()`·`Number.isNaN()` 네 문법을 요구하는 형태가 됐고, §2.1에서 정정한 실제 사용자에게는 첫 화면이 벽이 됐다.

스코프 방어선은 **§3.3 비범위 목록**과 **트랙 구성**이 맡는다. 레슨 수는 여기서 세지 않는다.

**대신 밀도를 고정한다.**

- 한 레슨은 **새 문법 하나**를 다룬다.
- 한 **단계**는 15~25분 안에 끝난다. (레슨이 아니라 단계 기준이다 — §2.1의 파편 시간 제약)

### 레슨의 단계 구성

레슨 하나는 여러 단계로 이루어진다. 모든 레슨이 6단계를 다 갖지는 않는다.

| 단계 | 학습자가 하는 일 | 검사 |
|---|---|---|
| `read` | 개념 설명을 읽는다. 코드도 실행도 없다 | 없음 |
| `run` | 완성된 예제를 실행 버튼으로 돌려 본다 | 없음 |
| `tweak` | 예제의 값 하나를 바꿔 결과가 어떻게 달라지는지 관찰한다 | 없음 |
| `fill` | 거의 다 주어진 코드에서 빈칸 하나를 채운다 | assert |
| `wrap` | `fill` 에서 쓴 식이 함수 안에 그대로 들어가 있다. 구체값을 붙잡아 둔 줄을 지우고 매개변수 이름으로 바꾼다 | assert |
| `write` | 빈 함수를 채운다 | assert |

쉬운 개념은 `read` → `fill` 로 끝나도 된다. 어려운 개념은 여섯 단계를 다 쓴다.

**진행 판정** — `read`는 다음으로 넘어갔는지, `run`은 실행 1회 이상, `tweak`은 코드를 바꾼 뒤 실행 1회 이상, `fill`·`wrap`·`write`는 assert 전부 통과. **어느 단계로든 자유롭게 이동할 수 있다.** 완료는 기록하되 통행은 막지 않는다.

### T0 — 진입 보조 트랙 (3레슨 · 12단계)

`read`·`run`·`tweak` 비중이 높다. 통과·실패가 있는 단계는 T0-3 의 `fill`·`write` 둘뿐이다.

| # | 제목 | 단계 | 다루는 문법 |
|---|---|---|---|
| 1 | 값에 이름 붙이기 | 3 (`read`·`run`·`tweak`) | 변수, `const` |
| 2 | 값을 눈으로 확인하기 | 3 (`read`·`run`·`tweak`) | `console.log` |
| 3 | 입력을 받아 결과 돌려주기 | 6 (+`run`·`fill`·`write`) | 함수, 매개변수, `return`, `console.log` 와의 차이 |

**T0-1·T0-2에 `fill`이 없는 이유:** `value` assert가 `entry` 함수를 요구하는데, 함수는 T0-3에서 처음 다룬다. 함수를 배우기 전에 함수로 검사할 수는 없다. 두 레슨은 통과·실패 없이 읽고 실행하고 바꿔 보는 것으로 끝낸다.

**`t0-03` 은 `run` 을 두 벌 둔다.** 뒤의 한 벌이 `return` 과 `console.log` 를 나란히 놓는 대비다 — 같은 일을 하는 함수 둘을 만들어, 하나는 `return` 하고 하나는 찍기만 한 뒤 각각의 결과를 변수에 담아 본다. 전면 감사에서 이 대비가 앱 전체에 **0곳**으로 나왔고, 학습자가 `t1-01` 쓰기에서 `return` 을 몰라 막힌 원인이 여기였다. 새 단계 종류를 만들지 않고 `run` 을 쓴 것은 하는 일이 '완성된 코드를 실행해 결과를 본다' 그대로이기 때문이다(`t5-05`·`t1-17` 선례).

**`t0-03` 에 `write` 를 신설했다.** 감사 결과 학습자는 T0·T1 전체에서 `function` 선언을 **한 번도 직접 쓰지 않았다** — 모든 `write` 의 starter 에 껍데기가 이미 적혀 있었다. `t0-03` `write` 의 starter 는 주석 한 줄뿐이라 함수를 통째로 쓴다. 검사는 `typeof` 까지만 볼 수 있어 다른 표기로도 통과하지만, 그 표기는 `t1-08` 이전 학습자에게 없는 문법이라 지문으로만 형태를 지정한다(F-010 선례).

**검사가 `return` 된 값만 본다는 사실은 `t0-03` `fill` 지문에서 알린다.** 그 단계가 앱에서 학습자가 검사를 처음 만나는 자리다.

**한 레슨이 새 문법 하나를 다룬다.** 순서는 난이도가 아니라 의존 관계다.

| # | 제목 | 단계 | 새로 다루는 문법 |
|---|---|---|---|

| 17 | 기다렸다가 결과 돌려주기 | 7 | `Promise`, `setTimeout`, 비동기 실행 순서 |

**단계 수가 4인 레슨(11·14)** 은 앞 레슨의 변형이라 `read`→`fill`→`wrap`→`write`로 끝낸다. T1 에 3단계 레슨은 없다. **단계 수가 6인 레슨(9)** 은 `tweak`을 둘 두었다 — 클로저는 "만드는 것과 부르는 것이 다르다"를 손으로 여러 번 확인해야 넘어간다. **`t1-17` 은 7단계다.** `run`·`tweak` 을 두 벌 둔다 — 앞의 한 벌은 `setTimeout`(맡기면 나중에 온다), 뒤의 한 벌은 `new Promise`(약속을 만든다)다. 앞 판은 `read`·`run`·`tweak` 이 전부 `setTimeout` 인데 `fill` 이 `new Promise` 를 처음 꺼내, 문법 하나가 아니라 개념 하나가 통째로 검사 단계에서 시작했다. 1·2·3·5·6·10·12·15 는 `fill` 과 `write` 사이에 `wrap`을 두었다 — 구체값 하나로 쓴 식을 매개변수로 넓히는 것만 따로 떼어 낸 단계다. `wrap`을 두지 않은 6레슨(4·7·8·9·16·17)은 남은 점프의 원인이 매개변수가 아니라 문법·구조·개념 결손이라 다리가 되지 않는다.

**초판과의 차이:** 초판은 T1을 8레슨으로 묶었고, 그 8개는 대부분 지금 각 주제의 마지막 `write` 단계로 살아 있다. 두 개는 배정이 바뀌었다 — `countByStatus`는 `for...of`를 쓰므로 조건문이 아니라 반복문(6)으로, `toCard`는 구조 분해와 전개를 함께 쓰므로 구조 분해가 아니라 전개(14)로 갔다.

**하나는 버렸다 — `finalPrice`(7).** "버린 것은 없다"고 적었던 앞 판을 정정한다. `finalPrice(price, discount)`는 `function` 선언문으로 조건 분기를 짜는 과제여서 레슨 주제(함수를 값처럼 다루기)와 무관했다. 화살표도 함수 표현식도 쓰지 않는다. `chooseRule`로 갈았다 — 이름을 받아 **그 이름에 맞는 함수를 돌려주는** 과제다. 이른 `return` 은 이 레슨이 다루던 부수 주제였고, `t1-02`의 `if`/`else if` 와 겹쳐 잃는 것이 없다.

**`t6-08` 은 도구가 보여주지 못하는 것을 지문이 대신 말한다.** 실행 프레임에 `allow-forms` 가 없어 **`submit` 이벤트가 아예 발생하지 않는다**(FINDINGS "T6 착수 전 실측 3건"). `sandbox` 는 `allow-scripts` 만 유지한다 — 그 규칙은 위험도 계산이 아니라 판단을 매번 하지 않기 위한 것이고, 한 번 열면 다음에는 다른 것이 각각 그럴듯한 이유를 갖고 온다. 그래서 학습자 코드는 `<form onSubmit>` + `preventDefault` 로 실무와 같게 두고, **"이 실행 환경에서는 폼 기본 제출이 막혀 있어 `preventDefault` 를 빠뜨려도 아무 일이 일어나지 않습니다. 실무에서는 페이지가 통째로 새로고침됩니다"** 를 read 에서 밝힌다. `class`/`className`(t3-01)·`0` 함정(t3-11)·훅 규칙(t4-05)과 같은 계열이다. tweak 은 `preventDefault` 누락 대신 다른 관찰로 바꿨다 — `type="button"` · 폼 밖 버튼 · 폼이 둘일 때 자기 폼만, 셋 다 실측으로 확정했다. **`submit` 이벤트는 `env` 의 무대 장치가 대신 쏜다**(캡처 단계 `click`·`keydown` 리스너). 학습자 코드는 실무와 같고 기본 동작만 없다.

**`<a href="#...">` 클릭은 프레임을 떠나게 한다.** `about:srcdoc` 에서 조각 이동은 같은 문서 안에서 끝나지 않고 프레임이 빈 문서가 된다(실측). 그래서 **해시 링크도 `env` 의 무대 장치가 가로채 `location.hash` 만 바꾼다.** 학습자 코드는 평범한 `<a href="#/courses">` 그대로다. 프렐류드는 이미 처리된 클릭에 경고를 찍지 않도록 한 줄만 고쳤다(`event.defaultPrevented`).

**실행 프레임이 sloppy mode 라는 것을 `t7-01` read 에서 밝힌다.** 실무의 모듈은 strict 라 떼어 낸 메서드의 `this` 가 `undefined` 인데 이 프레임에서는 `window` 다(실측: FINDINGS). 학습자가 `'use strict'` 한 줄로 실무 조건을 만들 수 있고, `t7-01` tweak ①이 그것이다. `class` 본문은 프레임과 무관하게 언제나 strict 라 `t7-07`~`t7-09` 는 왜곡이 없다.

초판은 7레슨이었다. `t8-06` 이 "나누는 기준" 과 "배럴 파일" 을 함께 지고 있어 **한 레슨은 새 개념 하나**라는 기준에 어긋났다. T1 이 8에서 17이 된 것과 같은 이유로 갈랐다.

**`t8-01` 이 export 누락 문구의 교재다.** `tweak` 로 네 갈래를 직접 밟는다 — 아무것도 안 내보냈을 때 / 이름이 다를 때 / `default` 로 내보냈을 때 / 내보냈는데 함수가 아닐 때. 검사기가 각각 다르게 말하고 고칠 곳도 다르다.

**`t8-05`~`t8-07` 이 React 다.** `t4-16` 이 학습자에게 "createContext 는 T8 에서 파일로 나눈다" 고 약속했고, 컴포넌트 분리를 실행 없이 `read` 로만 다루면 아래 금지 조항에 걸린다.

**왜 마지막인가.** 현재 러너는 사용자 코드를 **classic script**로 주입한다(`js/frame-doc.js`). `type="module"`로 바꾸면 M0에서 확보한 계약 넷이 동시에 열린다.

| 계약 | 근거 | 모듈로 바꾸면 | M4 의 답 |
|---|---|---|---|
| entry를 **전역 식별자**로 해석 | `js/validator.js` | 모듈 최상위는 `window`가 아님 | `files[]` 단계만 진입 모듈의 **네임스페이스**에서 찾는다. 없는 단계는 그대로 |
| 오류 줄번호 = `lineno - offsetOf(head)` (스칼라 1개) | `js/frame-doc.js` | 파일마다 좌표계가 달라짐 | 파일이 제 `blob` 이라 **줄 번호가 이미 파일 기준**이다. 보정을 끈다 |
| 상대 경로 해석 | 문서 URL이 `about:srcdoc` | 파일별 `blob:` + import map 로더 필요 | `'./이름'` 에서 `./` 를 떼고 **import map** 이 이름을 푼다 |
| React는 UMD 전역 | §6.1 | ESM과 섞이지 않음 → React 교체 | **교체하지 않았다.** UMD 는 classic script 로 먼저 들어가고 모듈 스코프에서 전역으로 보인다(실측) |

여기에 에디터 N개·탭 UI·파일별 저장 스키마가 얹힌다. **절반만 지어진 모듈 엔진을 T3 시점에 끌어들이면 T1·T2의 판정이 함께 흔들린다.**

**그래도 T3이 반쪽이 아닌 이유.** React 컴포넌트화의 어려운 부분은 prop 경계·상태 위치·리스트와 key·합성이며 전부 한 파일에서 다뤄진다. 파일 분리는 컴포넌트가 쌓인 뒤에 오는 포장 문제다.

**금지:** 파일을 이어붙이고 `import` 문을 무시하는 방식은 쓰지 않는다. 동작하지 않는 문법을 가르치는 것이다.

### 5.4 힌트를 넓히는 순서

`fill`·`wrap`·`write` 226단계 전부에 쓰지 않는다. 막히기 쉬운 곳부터 넓힌다. 세 기준의 합집합이 **132단계**이고, 그중 우선순위를 나눈다.

| 회차 | 대상 | 단계 수 | 고른 근거 |
|---|---|---:|---|
| 1 ✅ | 검사 개수 상위 | 12 | 검사 6개 이상은 226단계 중 28개뿐이다. 지문도 중앙값(222자)의 두 배를 넘는다 |
| 2 ✅ | FINDINGS 가 기록한 자리 | 5 | `t3-09`·`t4-13`·`t4-15`·`t6-02`·`t8-05`. **만드는 사람이 걸린 자리는 배우는 사람도 걸린다** |
| 3 ✅ | **T1 의 `fill`·`write` 전부** | 34 | 아래 참조 |
| 4 | T4 · T6 의 남은 `assert ≥ 4` | 34 | 두 트랙이 검사 부담의 절반을 진다(T4 27 · T6 20) |

| 7 | 각 레슨의 마지막 단계 중 남은 것 | 나머지 | 종합 단계는 앞의 것을 전부 끌어와야 한다 |

**3회차에서 T1 을 앞으로 당겼다.** 세 기준이 T1 을 **하나도 잡지 못한다**(`assert ≥ 4` 0개 · 긴 지문 0개). 그러나 그것은 T1 이 쉬워서가 아니라 **한 레슨이 문법 하나만 다루도록 잘게 쪼갠 결과**다. T1 을 8개에서 17개로 나눈 것이 바로 그 이유였다.

**검사 개수와 지문 길이는 난이도의 대리 지표일 뿐이고, 앞 트랙에서는 그 대리가 성립하지 않는다.** 그리고 T1 은 학습자가 가장 약한 구간이다 — 여기서 막혀 도구를 닫으면 뒤 트랙은 존재하지 않는 것과 같다.

**T1 힌트에는 기준이 하나 더 붙는다.** 그 단계에서 **처음 만나는 문법이 무엇인지 확인하고, 힌트가 그 문법 자체를 설명하지 않게 한다.** 설명은 `read` 단계가 이미 했다. 힌트는 "read 에서 본 그것을 여기 어디에 쓰는가" 를 가리킨다. 앞 레슨에서 이미 배운 것이라면 그 번호를 짚어 준다(예: "t1-02 에서 본 삼항 연산자가 그대로 들어갑니다").

**트랙별 현황** — `fill`·`write` 단계 수 / 힌트 있음 / `assert ≥ 4` / 지문 444자 이상 / 레슨의 마지막 단계.

## 6. 기술 설계

### 6.1 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 앱 | Vanilla JS (ES Modules) | 빌드 없음. 학습 대상을 학습 도구에 쓰지 않는다 |
| 에디터 | CodeMirror 6 (패키지 5개) | `@codemirror/state` · `view` · `commands` · `language` · `lang-javascript`. esm.sh ESM 임포트 |
| 트랜스파일 | **@babel/standalone** (`retainLines: true`) | 확정. 근거는 §6.3 |
| React | React 18 + ReactDOM UMD **개발 빌드** | iframe 내부에서만 로드. 개발 빌드는 선택이 아니라 **필수 결정**이다 — 아래 참조. **T8(엔진 M4)에서 ESM 전환 필요** |
| 스타일 | CSS 커스텀 프로퍼티 2단 토큰 (primitive → semantic) | 기존 프로젝트 규약 승계 |
| 저장 | `localStorage` | 서버 없음 |
| 배포 | GitHub Pages | `hotshin24` 계정 |

**UMD 라서 훅이 전역에 없다.** 빌드가 없으므로 React 를 UMD 로 불러오고, 그러면 훅은 `React` 객체 안에 들어 있어 `React.useState` 로 써야 한다. 실무의 `import { useState } from 'react'` 와 형태가 달라 그대로 두면 학습자가 T8 에서 혼란을 겪는다. 그래서 **T4 이후 모든 레슨의 starter 코드 맨 위에 `const { useState } = React;` 를 넣어 둔다.** 구조 분해(T1-13)라 새 문법이 아니고, 학습자가 쓰는 본문은 실무와 같아진다. **숨기지 않는다** — `t4-01` 의 `read` 가 이 제약과 이유를 설명하고, T8 에서 그 한 줄이 `import` 로 바뀔 뿐이라는 것까지 밝힌다.

**React 개발 빌드를 쓰는 이유.** production 빌드에서는 `class` 를 써도 `className` 과 결과가 **완전히 같다.** DOM 의 class 속성도, 적용된 스타일도, 콘솔도 같다. **잘못을 알 방법이 아예 없다.** §6.3 은 트랜스파일러 셋이 이것을 잡지 못한다는 것까지 알았고, **React 런타임도 잡지 못한다는 것은 T3 착수 전 실측에서 나왔다.** 학습자는 틀린 습관을 아무 신호 없이 굳히게 된다.

**T4 에서 더 필요해진다.** `key` 누락, 훅 규칙 위반, 조건부 훅 호출은 **전부 개발 빌드 전용 경고**다. 지금 production 으로 두면 T4 에서 다시 뒤집어야 한다.

**비용은 +1,023 KB · +118 ms** (142,586 B → 1,190,136 B, 220 ms → 338 ms). Babel(888 ms)과 병렬로 받으므로 체감 증가는 작고 §6.5 의 1.5s 기준 안이다. **다만 사용자 회선에서는 미측정이다.**

**T5 의 `fetch` 는 무대에 심은 가짜다.** 실행 프레임은 `sandbox="allow-scripts"` 라 origin 이 `null`(opaque)이고, 같은 호스트의 파일을 받는 것도 교차 출처 요청이 된다. GitHub Pages 는 `access-control-allow-origin: *` 를 보내 통과하지만 로컬 정적 서버는 보내지 않아 **로컬에서 진짜 요청이 전부 막힌다**(실측: FINDINGS "T5 착수 전 실측"). 배포판에서만 되는 레슨은 전수 회귀로 검증할 수 없다. `allow-same-origin` 을 붙이면 통과하지만 **그것은 절대 하지 않는다**(§6.4 보안). 그래서 레슨 `scaffold.html` 안 `<script>` 가 `window.fetch` 를 갈아 끼운다. 돌려주는 것은 진짜 `Response` 객체이므로 학습자 코드는 실무와 같고 응답만 우리가 정한다. **앱 코드 변경 0줄, 레슨 스키마 변경 0건.** `const { useState } = React` 와 같은 무대 장치이며 **숨기지 않는다** — `t5-06` read 가 밝힌다. 진짜 요청으로 바꾸고 싶어지면 필요한 것은 **프레임 권한이 아니라 CORS 헤더를 보내는 로컬 서버**다. T6 에서 같은 결정을 다시 한다.

**`codemirror` 메타 패키지를 쓰지 않는 이유:** 그 패키지의 `basicSetup` 은 autocomplete·lint·search·fold 를 통째로 끌고 온다. 필요한 확장만 직접 조립한다 — 실제로 쓰는 것은 `lineNumbers` · `history` · `bracketMatching` · `indentOnInput` · `syntaxHighlighting` · `javascript` 와 커스텀 Tab 키맵이다.

**`@codemirror/state` 사본은 반드시 1개여야 한다.** CDN 에서 패키지를 따로 가져오면 사본이 둘 생기고 CM6 가 확장을 거부한다. `?deps=@codemirror/state@6` 로 한 버전에 고정한다.

**CDN 실패 시 `textarea` 로 폴백한다.** 학습이 CDN 가용성에 인질로 잡히면 안 된다. 폴백되면 학습자에게 알린다 — 구문 강조가 없는 화면을 보고 도구가 고장났다고 판단하게 두지 않는다.

### 6.3 트랜스파일러 — **확정: @babel/standalone**

**초판의 잠정 결정(Sucrase)을 뒤집는다.** 실측 근거는 `docs/FINDINGS.md` 의 "트랜스파일러 실측".

| 후보 | 크기(압축 해제) | 파일 수 | 콜드 로드 | 변환 1회 | 줄 번호 | 에러 위치 |
|---|---:|---:|---:|---:|---|---|
| Sucrase 3.35 | 246 KB | 16 | 973 ms | 0.29 ms | 보존 | **항상 `1:16`** |
| **@babel/standalone 7.26** | 2,903 KB | 2 | **888 ms** | 0.76 ms | **`retainLines` 로 보존** | 정확 + 코드 프레임 |
| esbuild-wasm 0.24 | 11,722 KB | 3+wasm | 1,689 ms | 10.03 ms | 깨짐 | 정확 |

**Sucrase 를 배제한 이유 둘.**

**(1) 에러 위치가 실제 오류와 무관하다.** JSX 구문 오류 세 가지(닫는 태그 누락 · 중괄호 짝 안 맞음 · 여러 요소 미포장)를 모두 `Unexpected token, expected ";" (1:16)` 으로 보고했다. `1:16` 은 `const App = () => {` 의 화살표 위치이며 어떤 실수를 하든 같은 값이 나온다. **이 제품은 정확한 줄 번호를 M0 에서 확보하고 F-006 에서 지켜냈고 T2 에서 scaffold 를 넣으며 실행 시점 계산으로 다시 지켰다.** 4행의 오타를 1행에서 찾게 만드는 트랜스파일러는 그 자산을 무효화한다. §2.1 의 학습자는 이 상황에서 자기 코드가 아니라 도구를 의심한다.

**(2) 크기가 11배 작은데 콜드 로드는 더 느리다.** Sucrase 246 KB / 973 ms, Babel 2,903 KB / 888 ms. Sucrase 의 모듈 그래프가 **16파일**이라 왕복이 쌓이고, Babel 은 **2파일**이다. "작으니 빠를 것" 이라는 초판의 전제가 실측에서 성립하지 않았다.

**줄 번호는 `retainLines: true` 로 해결된다 — 실측.** 입력 11행 중 10행의 마커가 기본 옵션에서는 8행으로 밀렸고(출력 9행), `retainLines: true` 에서는 **10행 그대로**였다(출력 11행). Babel 을 배제할 유일한 기술적 이유였던 항목이 사라진다. **소스맵이 필요 없으므로 `runner.js` 의 `lineno - offsetOf(head)` 산술을 그대로 쓴다.**

**크기 부담은 감당 가능하다.** 콜드 888 ms 로 셋 중 가장 빠르고 §6.5 의 "T3/T4 첫 실행 1.5s" 안이다. 트랜스파일러는 §6.5 대로 **T3 진입 시에만** 로드되므로 T1·T2 의 로드 비용(F-007)에 영향이 없다. 진입은 1회이고 이후 캐시된다.

**esbuild-wasm 을 배제한 이유.** 11.7 MB · 1,689 ms 로 1.5s 기준을 초과한다. 줄 번호가 입력 10행 → 출력 4행으로 깨져(출력 6행) **소스맵 배관이 추가로 필요하고**, 그러면 위 산술을 소스맵 조회로 갈아야 한다. 변환 1회도 10.03 ms 로 가장 느리다 — 매 변환이 wasm 워커 경계를 넘는다. 세 축 모두에서 지고 얻는 것이 없다.

**세 후보 모두 잡지 못하는 것: `class` vs `className`.** JSX 구문으로는 유효해서 파서를 통과한다. 검사로 걸러지지 않으므로 **레슨 설계에서 다룬다 — T3-1(JSX 문법과 HTML 의 차이)이 그 자리다.**

**M2 에서 확인할 것** — `retainLines` 가 여러 줄 JSX 에서도 정렬을 유지하는지, 그 옵션이 `offsetOf(head)` 오프셋과 맞물리는지, 트랜스파일 단계의 에러를 `window.onerror` 가 아니라 그 자리에서 잡아 코드 프레임째 콘솔로 넘길 것인지.

### 6.4 레슨 데이터 스키마

**단계 레벨 `env` 필드 — 무대가 아니라 환경이다.** `scaffold` 와 성격이 다르므로 나란히 두지 않고 따로 세웠다.

| | `scaffold` | `env` |
|---|---|---|
| 무엇인가 | **학습자가 조작할 무대.** 코드가 손댈 DOM 과 그 스타일 | **환경.** 그 레슨에서 세상이 어떻게 동작하는지 |
| 예 | 상품 카드 목록, 검색 폼, `#root` | 가짜 `fetch`, 응답 지연, 404 를 돌려주는 주소 |
| 학습자가 보는가 | 미리보기 패널에 보인다 | 보이지 않는다. `read` 지문이 밝힌다 |
| 형태 | `{ html, css }` (줄 배열 또는 문자열) | 줄 배열 또는 문자열. `<script>` 로 주입된다 |
| 주입 위치 | 사용자 코드 **앞의 본문** | 프렐류드 **뒤**, 사용자 코드 **앞** |

**미리보기 패널 판정이 `scaffold.html` 유무를 보는 이유가 이 구분에서 나온다.** 패널은 "보여줄 무대가 있는가" 로 켜져야 한다. 무대가 무대만 담으면 `scaffold.html` 이 있다는 것이 곧 보여줄 것이 있다는 뜻이 된다. 환경을 같은 필드에 섞으면 그 등식이 깨진다 — `t5-06`~`t5-09` 처럼 가짜 `fetch` 만 필요하고 그릴 것은 없는 레슨에서 **빈 패널이 열린다.** 그래서 `preview.isOn()` 을 고치는 대신 데이터를 갈랐다. 판정 주체는 그대로 레슨 데이터다.

빈 패널을 감추려고 설명용 마크업을 `scaffold.html` 에 채우는 방법은 택하지 않았다. 보여줄 것이 없는데 패널을 켜 놓고 그 안을 메우는 우회이고, 무대와 환경의 구분을 코드가 아니라 눈속임으로 옮기는 일이다.

**주입은 `env` 가 있을 때만 한다.** 없으면 head 는 한 글자도 달라지지 않는다. 줄 번호는 `offsetOf` 가 최종 head 를 세므로 자동으로 맞는다. 앱 코드 변경은 4파일 9줄이다 — `lessons.js`(정규화) · `frame-doc.js`(주입) · `runner.js`·`main.js`(전달). `preview.js` 는 건드리지 않았다.

**단계 레벨 `files[]` 필드 — 여러 파일로 이루어진 단계.** T8(모듈)이 여기 걸려 있다.

```json
{
  "kind": "write",
  "entry": "doubleAll",
  "files": [
    { "name": "main.js", "entry": true,
      "code": ["import { double } from './utils.js';", ""],
      "solutionCode": ["…"] },
    { "name": "utils.js", "readOnly": true,
      "code": ["export const double = (n) => n * 2;"] }
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `name` | 파일 이름. 지정자 해석의 키. 중복 금지. 하위 디렉터리 없음 |
| `entry` | **정확히 하나**의 파일에 `true`. 이 파일부터 불러온다 |
| `code` · `solutionCode` | 파일별. 줄 배열 또는 문자열 |
| `readOnly` | 참고 파일. 편집기에서 잠그고 저장하지 않는다. `solutionCode` 를 둘 수 없다 |
| 순서 | **배열 순서가 곧 탭 순서.** 순서 필드를 따로 두지 않는다 |

**단어 하나가 두 층에서 다른 뜻이다.** 파일의 `entry` 는 "어느 파일부터 불러오는가", 단계의 `entry` 는 "그 파일에서 무엇을 검사하는가"다. 층이 다르므로 이름을 바꾸지 않았다. 검사기는 전역이 아니라 진입 모듈의 네임스페이스에서 그 이름을 찾는다 — 모듈 안의 `export` 는 `window` 에 붙지 않는다.

**`files` 와 `code`/`solutionCode` 를 함께 둘 수 없다.** 어느 쪽이 이기는지 규칙을 만들면 반드시 틀린다. 레슨 로드에서 거절한다. `runtime: 'react'` 와의 조합도 거절한다 — 실측하지 않았다.

동작 계약과 알려진 한계는 기능정의서 §8 에 있다.

**레슨 레벨 `runtime` 필드** — `'js'`(기본) 또는 `'react'`. 생략하면 `'js'` 이므로 기존 레슨 파일은 고치지 않는다. 트랙 접두어나 코드에 JSX 가 있는지로 추측하지 않는다 — 그렇게 하면 판정이 파일명 규칙이나 문자열 추측에 얹힌다. `'react'` 인 레슨만 Babel 과 React UMD 를 받고, 그 외에는 요청이 나가지 않는다.


M1a에서 구현·검증된 `schemaVersion: 1`. 아래는 실제 동작하는 형태다(`lessons/t1-03.json`).

```json
{
  "schemaVersion": 1,
  "id": "t1-03",
  "track": "T1",
  "order": 3,
  "title": "map으로 배열 변환하기",
  "brief": [
    "첫 번째 문단",
    "두 번째 문단"
  ],
  "entry": "doubleAll",
  "starterCode": "function doubleAll(numbers) {\n  // 여기를 채우세요\n}\n",
  "solutionCode": "function doubleAll(numbers) {\n  return numbers.map((n) => n * 2);\n}\n",
  "asserts": [
    {
      "type": "value",
      "label": "[1, 2, 3] → [2, 4, 6]",
      "args": [[1, 2, 3]],
      "expected": [2, 4, 6]
    }
  ]
}
```

**필드**

"앱 사용 여부"는 현재 앱 코드가 그 필드를 읽는지를 뜻한다. 데이터에 들어 있는 것과 앱이 쓰는 것은 다르다.

| 필드 | 필수 | 앱 사용 여부 | 비고 |
|---|---|---|---|
| `schemaVersion` | ✔ | 사용 | `1` 이외는 로드 거부 |
| `id` | ✔ | 사용 | 파일 경로를 만든다. 파일명과 일치해야 한다 |
| `track` | ✔ | 데이터에만 존재 | |
| `title` · `brief` | ✔ | 사용 | `brief`는 **문자열 배열(문단 단위)**. 초안의 마크다운 단일 문자열에서 변경 |
| `entry` | 조건부 | 사용 | `value` assert가 하나라도 있으면 필수. 유효한 식별자여야 한다 |
| `starterCode` | ✔ | 사용 | 최초 로드와 리셋에 쓴다 |
| `solutionCode` | ✔ | 사용 | 검증에 쓰고, 정답 보기(F-11)가 펼쳐 보여 준다 |
| `asserts` | — | 사용 | 없으면 실행만 하고 판정하지 않는다 |
| `order` | — | 데이터에만 존재 | 파일명·`id`의 순번과 일치해야 한다 |
| `hints`(단계) | — | 사용 | F-18. 최대 2개로 자른다. 지금은 51단계에 있다 (§5.4) |
| `reference` | — | 미도입 | F-19 가 앞 단계에서 자동으로 고르므로 저자가 적을 것이 없다 |
| `estimatedMin` | — | 미도입 | 데이터에도 없다 |
| `runtime`(레슨) · `env`(단계) | — | 사용 | v2 에서 도입. 위 설명 참조 |

**`brief`를 마크다운에서 문단 배열로 바꾼 이유:** 마크다운을 쓰려면 파서를 붙이거나 `innerHTML`을 써야 한다. 파서는 의존성 추가고, `innerHTML`은 레슨 데이터를 신뢰 입력으로 만든다. 문단 배열이면 `textContent`로 안전하게 그린다. 서식이 실제로 필요해지는 시점에 다시 판단한다.

**`entry`를 무조건 필수로 두지 않는 이유:** T2(DOM·이벤트)는 진입 함수가 없는 레슨이 나온다. `value` assert가 있을 때만 요구한다.

**assert 타입 로드맵:** `value`(반환값, **M1a 구현**) · `console`(출력) · `dom`(선택자+텍스트/속성) · `html`(정규화 비교) · `manual`(참고 답안 비교만)

**`value` assert 계약**

- 읽는 대상은 **`entry`로 지정한 함수의 반환값**이다. 마지막 표현식이 아니다 — 학습자가 디버깅용 `console.log`를 끝에 붙이면 완료값이 바뀌어 레슨이 깨지고, 완료값을 얻으려면 `eval`이 필요해 §6.2에서 확보한 줄 번호 정확도가 무너진다.
- `args`를 펼쳐 호출하고 `expected`와 깊은 비교한다. 비교와 표시 문자열 생성은 **iframe 내부**에서 한다(구조화 복제로 함수·순환 참조가 부모로 넘어오지 못한다).
- 결과는 **3상태**다.

| 상태 | 의미 | 표시 |
|---|---|---|
| `pass` | 반환값이 `expected`와 일치 | `통과 — {label}` |
| `fail` | 반환값이 다름 | `실패 — {label}` + 기대값/실제값 |
| `error` | 함수를 못 찾았거나 호출이 예외로 끝남 | `오류 — {label} · {message}` |

  `fail`과 `error`를 나누는 이유: 학습자가 봐야 할 다음 지점이 다르다. 전자는 로직, 후자는 함수 이름이나 문법이다.
- **에러 선행 규칙:** 사용자 코드에 에러가 있으면 assert 목록 대신 `코드에 에러가 있어 검사하지 못했습니다.`를 표시한다. 구문 에러가 나면 사용자 코드 스크립트만 죽고 assert 스크립트는 그대로 돌아 `함수를 찾을 수 없습니다`가 뜨는데, 진짜 원인은 문법이기 때문이다. `error` 메시지가 `assert`보다 먼저 도착하는 점을 이용해 구분한다.
- **비동기 반환값:** 반환값이 thenable 이면 `await` 한 뒤 `expected`와 비교한다. Promise 자체를 비교하면 어떤 답도 통과할 수 없다. 비동기 assert 하나가 **2초** 안에 완료되지 않으면 `error` 로 끊는다 — 워치독은 이벤트 루프가 살아 있는 프레임에 개입하지 않으므로 이 층에서 막아야 한다. reject 는 `error` 로만 보고하며 거부 값을 검사하지 않는다.
- **실행 순서:** 사용자 코드 → assert 전부(비동기면 완료까지) → `done`.
- **`done`의 정의:** **"이번 실행의 판정이 전부 끝났다."** 프레임 종료가 아니다 — `done` 이후에도 프레임은 살아 있고 워치독의 감시 대상으로 남는다. M0 시절에는 "동기 실행 완료"였으나 비동기 assert 도입과 함께 넓혔다(FINDINGS F-005).
