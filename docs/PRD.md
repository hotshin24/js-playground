## 0. 전제 하나

이 문서는 "학습용 도구"를 정의한다. 그런데 이 도구를 만드는 과정 자체가 이 도구로 배우려는 내용(DOM, 이벤트, 상태 관리, 모듈 설계)의 실전판이다. 도구 완성이 목표가 아니라 **도구를 만들면서 T1~T2를 통과하고, 완성된 도구로 T3~T4를 통과하는 것**이 실제 시나리오다. 스코프 판단은 전부 이 기준으로 한다.

## 1. 문제 정의

### 1.1 현재 상황

13년 커머스 경력 후 웹퍼블리싱으로 전환. HTML/CSS는 대규모 프로젝트 2건(392p, 164p)으로 검증된 상태. 그러나 JS/React는 다음 지점에서 막힌다.

| 구분 | 현재 | 목표 |
|---|---|---|
| HTML/CSS | 대규모 실전 경험 | 유지 |
| JS | 코드를 읽을 수는 있음 | 백지에서 작성 |
| React | 개념만 인지 | 마크업을 컴포넌트로 분해 |

### 1.2 기존 학습 수단의 한계

| 수단 | 한계 |
|---|---|
| 강의/책 | 예제가 남의 코드다. 내 마크업과 연결되지 않는다 |
| CodePen·CodeSandbox | 자유도는 높지만 커리큘럼이 없다. 뭘 해야 할지가 없다 |
| 온라인 코딩 문제 | 알고리즘 중심. 퍼블리셔가 실무에서 쓰는 DOM/이벤트/상태와 무관 |
| 프로젝트 클론 | 난이도 점프가 크다. 중간 단계가 비어 있다 |

**핵심 결핍: "내가 이미 만든 마크업"을 교재로 쓰는 학습 경로가 없다.**

### 1.3 제품 가설

정적 사이트 한 페이지 안에서 (1) 문제 제시 (2) 코드 작성 (3) 즉시 실행 (4) 자동 검증이 한 화면에 붙어 있고, 교재가 **JW Anderson·HOOT UP의 실제 마크업**이면, 퍼블리싱 → JS → React 전환의 심리적·기술적 간극이 줄어든다.

## 2. 사용자

### 2.1 유일 페르소나

- 43세, 웹퍼블리셔 전환 중, 구직 활동 병행
- CSS 아키텍처(토큰, `:is()` 압축, 시맨틱 알리아스)에는 강함
- 접근성·문서화에 대한 기준이 높음 → 도구 자체도 그 기준을 만족해야 사용을 지속함
- 학습 시간은 구직 활동 사이의 파편 시간 → **한 세션 15~25분 안에 한 단계가 끝나야 함**

**JS 문법 지식은 백지에 가깝다.** 변수·`console.log`·함수가 각각 무엇인지 정확히 설명하지 못하는 상태에서 시작한다. 코드를 읽으면 대강 무슨 일이 일어나는지는 짐작하지만, 빈 화면에서 한 줄을 쓰지는 못한다.

> **정정 이력 (v0.4)** — 초판은 "CSS 아키텍처에 강함 → 추상화·구조화 사고는 이미 있다"고 적었다. **이 추론은 틀렸다.** CSS 설계 역량과 JS 문법 지식은 별개다. 이 오류가 레슨 설계에 그대로 옮겨져, 첫 레슨이 `typeof`·`Number()`·`String()`·`Number.isNaN()`을 한꺼번에 요구하는 형태가 됐다. 실제 사용자에게는 전부 처음 보는 단어다. 레슨 구조 재설계(T0 트랙 신설, 단계 분할)는 이 정정에서 나온 결과다.

### 2.2 사용 맥락

| 맥락 | 요구 |
|---|---|
| 노트북, 카페 | 오프라인/저속 회선에서도 초기 로드가 버티는 용량 |
| 짧은 세션 | 이어하기 — 진행률과 마지막 코드가 보존 |
| 구직 중 | 학습 흔적이 곧 근거가 되도록 진행 기록이 남음 |

## 3. 제품 정의

### 3.1 한 줄 정의

> 마크업을 이미 쓸 줄 아는 사람이, 그 마크업을 재료로 JS와 React를 손으로 익히는 정적 웹 플레이그라운드.

### 3.2 설계 원칙

1. **한 화면에서 끝난다** — 탭 이동, 페이지 이동 없음
2. **교재는 내 코드다** — 예제 마크업은 실제 포트폴리오에서 발췌
3. **틀린 걸 도구가 알려준다** — 눈으로 비교하지 않고 검증이 판정
4. **레슨은 데이터다** — 레슨 추가에 애플리케이션 코드 수정이 필요 없어야 한다
5. **도구가 학습을 방해하지 않는다** — 무한루프, 로딩 지연, 상태 소실은 학습 중단 사유다

### 3.3 명시적 비범위 (Out of Scope)

| 제외 항목 | 사유 |
|---|---|
| 서버 / DB / 로그인 | 정적 배포 전제. 사용자 1명 |
| npm 패키지 임의 설치 | 브라우저 번들러 필요. 비용 대비 학습 효과 낮음 |
| TypeScript | JS를 먼저 확보. v2 이후 |
| 다중 파일 프로젝트 | MVP는 단일 파일. 파일 분리는 T4 종료 후 별도 판단 |
| 공유 링크 / 협업 | 사용자 1명. v2에서 URL 인코딩으로 검토 |
| 자동 채점 점수·랭킹 | 게임화 불필요. 통과/미통과만 |
| 모바일 코드 작성 | 뷰어(읽기)까지만 지원. 편집은 데스크톱 |

## 4. 학습 트랙 구조

**트랙은 고정, 레슨 수는 고정하지 않는다.**

초판은 "트랙 4개 × 레슨 8개 = 총 32레슨 고정"을 스코프 방어선으로 삼았다. **이 방어선은 스코프가 아니라 밀도를 눌렀다.** 8개에 맞추려다 T1-1 하나가 `typeof`·`Number()`·`String()`·`Number.isNaN()` 네 문법을 요구하는 형태가 됐고, §2.1에서 정정한 실제 사용자에게는 첫 화면이 벽이 됐다.

스코프 방어선은 **§3.3 비범위 목록**과 **트랙 구성**이 맡는다. 레슨 수는 여기서 세지 않는다.

**대신 밀도를 고정한다.**

- 한 레슨은 **새 문법 하나**를 다룬다.
- 한 **단계**는 15~25분 안에 끝난다. (레슨이 아니라 단계 기준이다 — §2.1의 파편 시간 제약)

### 레슨의 단계 구성

레슨 하나는 여러 단계로 이루어진다. 모든 레슨이 5단계를 다 갖지는 않는다.

| 단계 | 학습자가 하는 일 | 검사 |
|---|---|---|
| `read` | 개념 설명을 읽는다. 코드도 실행도 없다 | 없음 |
| `run` | 완성된 예제를 실행 버튼으로 돌려 본다 | 없음 |
| `tweak` | 예제의 값 하나를 바꿔 결과가 어떻게 달라지는지 관찰한다 | 없음 |
| `fill` | 거의 다 주어진 코드에서 빈칸 하나를 채운다 | assert |
| `write` | 빈 함수를 채운다 | assert |

쉬운 개념은 `read` → `fill` 로 끝나도 된다. 어려운 개념은 다섯 단계를 다 쓴다.

**진행 판정** — `read`는 다음으로 넘어갔는지, `run`은 실행 1회 이상, `tweak`은 코드를 바꾼 뒤 실행 1회 이상, `fill`·`write`는 assert 전부 통과. **어느 단계로든 자유롭게 이동할 수 있다.** 완료는 기록하되 통행은 막지 않는다.

### T0 — 진입 보조 트랙 (3레슨)

| # | 주제 | 다루는 것 |
|---|---|---|
| 1 | 변수 | 값에 이름을 붙인다는 것 |
| 2 | `console.log` | 값을 눈으로 확인하는 방법 |
| 3 | 함수 | 입력을 받아 결과를 돌려주는 것 |

`read`·`run`·`tweak` 비중을 높게 잡는다. `write` 단계는 없어도 된다. **T0는 JS 이전 단계라 성격이 다르므로 트랙으로 분리한다.** 스코프 방어선의 "트랙 4개"는 T1~T4를 가리키며, T0는 진입 보조 트랙으로 여기에 포함하지 않는다.

### T1 — JS 기초 문법 (문법 단위로 재분할)

아래 8개 표는 **초판의 묶음 단위**이며, 현재 이 묶음은 문법 단위로 다시 쪼개는 중이다(값과 타입 / 형변환 / 함수 선언과 반환 / 화살표 함수 / 스코프와 클로저 / 배열 기초 / `map` / `filter` / `reduce` / 객체 기초 / 구조 분해 / 전개 / 조건문 / 반복문 / 템플릿 리터럴 / 모듈 패턴 / 비동기 기초). **기존 8레슨은 각 주제의 마지막 `write` 단계로 재활용한다. 버리지 않는다.**


| # | 주제 | 검증 방식 |
|---|---|---|
| 1 | 변수·타입·형변환 | 반환값 assert |
| 2 | 함수·화살표 함수·스코프 | 반환값 assert |
| 3 | 배열 메서드 (map/filter/reduce) | 반환값 assert |
| 4 | 객체·구조 분해·전개 연산자 | 반환값 assert |
| 5 | 조건·반복 리팩터링 | 반환값 assert |
| 6 | 템플릿 리터럴로 HTML 문자열 생성 | 문자열 정규화 비교 |
| 7 | 모듈 패턴 (import/export) | 반환값 assert |
| 8 | 비동기 기초 (Promise / async·await / fetch) | 비동기 assert |

*설계 메모: 6번은 T2·T3의 다리 역할. 마크업을 데이터로부터 만드는 첫 경험.*

### T2 — DOM · 이벤트 인터랙션 (8레슨)

| # | 주제 | 실습 소재 |
|---|---|---|
| 1 | 선택·순회 (querySelector / closest / dataset) | 카드 리스트 |
| 2 | 클래스·속성 조작 | 탭 UI |
| 3 | 이벤트 바인딩과 이벤트 객체 | 버튼 그룹 |
| 4 | 이벤트 위임 | 상품 리스트 (JW Anderson 발췌) |

### T3 — 퍼블리싱 → React 컴포넌트 전환 (8레슨) ★ 핵심 트랙

이 트랙이 이 제품의 존재 이유다. 좌측 패널에 **실제 프로젝트 마크업**이 주어지고, 우측에서 그것을 컴포넌트로 옮긴다.

| # | 주제 | 소재 |

| 1 | JSX 문법과 HTML의 차이 (class→className, self-closing) | 버튼 |
| 2 | 첫 컴포넌트 — 마크업 그대로 감싸기 | 상품 카드 |
| 3 | props로 하드코딩 값 뽑아내기 | 상품 카드 → `<ProductCard>` |
| 4 | 리스트 렌더링과 key | 상품 그리드 |
| 5 | children과 합성 (composition) | 섹션 래퍼 |
| 6 | 조건부 렌더링 (품절/뱃지/할인) | 상품 카드 변형 |
| 7 | 컴포넌트 분해 기준 — 어디서 자를 것인가 | 코스 카드 (HOOT UP) |
| 8 | CSS 연결 전략 (전역 클래스 유지 vs CSS Modules 개념) | 종합 |

*설계 메모: 7번은 정답이 하나가 아니다. 검증 대신 "참고 답안 비교" 모드로 처리한다.*

| F-11 | 리셋 / 정답 보기 | 초기 코드 복원, 참고 답안 토글 (통과 후 또는 3회 실패 후 노출) |

## 6. 기술 설계

### 6.1 스택

| 영역 | 선택 | 비고 |
|---|---|---|
| 앱 | Vanilla JS (ES Modules) | 빌드 없음. 학습 대상을 학습 도구에 쓰지 않는다 |
| 에디터 | CodeMirror 6 (패키지 5개) | `@codemirror/state` · `view` · `commands` · `language` · `lang-javascript`. esm.sh ESM 임포트 |
| 트랜스파일 | Sucrase 또는 @babel/standalone | §6.3 참조 |
| React | React 18 + ReactDOM UMD | iframe 내부에서만 로드 |
| 스타일 | CSS 커스텀 프로퍼티 2단 토큰 (primitive → semantic) | 기존 프로젝트 규약 승계 |
| 저장 | `localStorage` | 서버 없음 |
| 배포 | GitHub Pages | `hotshin24` 계정 |

**`codemirror` 메타 패키지를 쓰지 않는 이유:** 그 패키지의 `basicSetup` 은 autocomplete·lint·search·fold 를 통째로 끌고 온다. 필요한 확장만 직접 조립한다 — 실제로 쓰는 것은 `lineNumbers` · `history` · `bracketMatching` · `indentOnInput` · `syntaxHighlighting` · `javascript` 와 커스텀 Tab 키맵이다.

**`@codemirror/state` 사본은 반드시 1개여야 한다.** CDN 에서 패키지를 따로 가져오면 사본이 둘 생기고 CM6 가 확장을 거부한다. `?deps=@codemirror/state@6` 로 한 버전에 고정한다.

**CDN 실패 시 `textarea` 로 폴백한다.** 학습이 CDN 가용성에 인질로 잡히면 안 된다. 폴백되면 학습자에게 알린다 — 구문 강조가 없는 화면을 보고 도구가 고장났다고 판단하게 두지 않는다.

### 6.4 레슨 데이터 스키마

M1a에서 구현·검증된 `schemaVersion: 1`. 아래는 실제 동작하는 형태다(`lessons/t1-03.json`).

```json
{
  "schemaVersion": 1,
  "id": "t1-03",
  "track": "T1",
  "order": 3,
  "title": "map으로 배열 변환하기",
  "brief": [
    "첫 번째 문단",
    "두 번째 문단"
  ],
  "entry": "doubleAll",
  "starterCode": "function doubleAll(numbers) {\n  // 여기를 채우세요\n}\n",
  "solutionCode": "function doubleAll(numbers) {\n  return numbers.map((n) => n * 2);\n}\n",
  "asserts": [
    {
      "type": "value",
      "label": "[1, 2, 3] → [2, 4, 6]",
      "args": [[1, 2, 3]],
      "expected": [2, 4, 6]
    }
  ]
}
```

**필드**

"앱 사용 여부"는 현재 앱 코드가 그 필드를 읽는지를 뜻한다. 데이터에 들어 있는 것과 앱이 쓰는 것은 다르다.

| 필드 | 필수 | 앱 사용 여부 | 비고 |
|---|---|---|---|
| `schemaVersion` | ✔ | 사용 | `1` 이외는 로드 거부 |
| `id` | ✔ | 사용 | 파일 경로를 만든다. 파일명과 일치해야 한다 |
| `track` | ✔ | 데이터에만 존재 | |
| `title` · `brief` | ✔ | 사용 | `brief`는 **문자열 배열(문단 단위)**. 초안의 마크다운 단일 문자열에서 변경 |
| `entry` | 조건부 | 사용 | `value` assert가 하나라도 있으면 필수. 유효한 식별자여야 한다 |
| `starterCode` | ✔ | 사용 | 최초 로드와 리셋에 쓴다 |
| `solutionCode` | ✔ | 데이터에만 존재 | 정답 보기(F-11) 미구현. 현재는 검증용으로만 쓴다 |
| `asserts` | — | 사용 | 없으면 실행만 하고 판정하지 않는다 |
| `order` | — | 데이터에만 존재 | 파일명·`id`의 순번과 일치해야 한다 |
| `estimatedMin` · `hints` | — | 미도입 | 데이터에도 없다 |
| `reference` · `runtime` | — | 미도입 | T3 진입 시 필요 |

**`brief`를 마크다운에서 문단 배열로 바꾼 이유:** 마크다운을 쓰려면 파서를 붙이거나 `innerHTML`을 써야 한다. 파서는 의존성 추가고, `innerHTML`은 레슨 데이터를 신뢰 입력으로 만든다. 문단 배열이면 `textContent`로 안전하게 그린다. 서식이 실제로 필요해지는 시점에 다시 판단한다.

**`entry`를 무조건 필수로 두지 않는 이유:** T2(DOM·이벤트)는 진입 함수가 없는 레슨이 나온다. `value` assert가 있을 때만 요구한다.

**assert 타입 로드맵:** `value`(반환값, **M1a 구현**) · `console`(출력) · `dom`(선택자+텍스트/속성) · `html`(정규화 비교) · `manual`(참고 답안 비교만)

**`value` assert 계약**

- 읽는 대상은 **`entry`로 지정한 함수의 반환값**이다. 마지막 표현식이 아니다 — 학습자가 디버깅용 `console.log`를 끝에 붙이면 완료값이 바뀌어 레슨이 깨지고, 완료값을 얻으려면 `eval`이 필요해 §6.2에서 확보한 줄 번호 정확도가 무너진다.
- `args`를 펼쳐 호출하고 `expected`와 깊은 비교한다. 비교와 표시 문자열 생성은 **iframe 내부**에서 한다(구조화 복제로 함수·순환 참조가 부모로 넘어오지 못한다).
- 결과는 **3상태**다.

| 상태 | 의미 | 표시 |
|---|---|---|
| `pass` | 반환값이 `expected`와 일치 | `통과 — {label}` |
| `fail` | 반환값이 다름 | `실패 — {label}` + 기대값/실제값 |
| `error` | 함수를 못 찾았거나 호출이 예외로 끝남 | `오류 — {label} · {message}` |

  `fail`과 `error`를 나누는 이유: 학습자가 봐야 할 다음 지점이 다르다. 전자는 로직, 후자는 함수 이름이나 문법이다.
- **에러 선행 규칙:** 사용자 코드에 에러가 있으면 assert 목록 대신 `코드에 에러가 있어 검사하지 못했습니다.`를 표시한다. 구문 에러가 나면 사용자 코드 스크립트만 죽고 assert 스크립트는 그대로 돌아 `함수를 찾을 수 없습니다`가 뜨는데, 진짜 원인은 문법이기 때문이다. `error` 메시지가 `assert`보다 먼저 도착하는 점을 이용해 구분한다.
- **비동기 반환값:** 반환값이 thenable 이면 `await` 한 뒤 `expected`와 비교한다. Promise 자체를 비교하면 어떤 답도 통과할 수 없다. 비동기 assert 하나가 **2초** 안에 완료되지 않으면 `error` 로 끊는다 — 워치독은 이벤트 루프가 살아 있는 프레임에 개입하지 않으므로 이 층에서 막아야 한다. reject 는 `error` 로만 보고하며 거부 값을 검사하지 않는다.
- **실행 순서:** 사용자 코드 → assert 전부(비동기면 완료까지) → `done`.
- **`done`의 정의:** **"이번 실행의 판정이 전부 끝났다."** 프레임 종료가 아니다 — `done` 이후에도 프레임은 살아 있고 워치독의 감시 대상으로 남는다. M0 시절에는 "동기 실행 완료"였으나 비동기 assert 도입과 함께 넓혔다(FINDINGS F-005).

## 부록 A. 이 문서의 개정 규칙

- §3.3(비범위)과 §4(트랙 구성·밀도 기준)를 변경할 때는 버전을 올리고 변경 사유를 기록한다.
- **페르소나(§2.1)를 정정할 때는 정정 이력을 본문에 남긴다.** 지운 전제는 설계에 이미 옮겨가 있어서, 지우기만 하면 왜 그렇게 만들었는지가 사라진다.
- §6.3, §10의 미결 항목은 결정 즉시 본문에 반영하고 열린 질문에서 삭제한다.
- 측정값(성공 지표, 성능)은 **실측치만** 기재한다. 추정치는 기재하지 않는다.
