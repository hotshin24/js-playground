## 1. 실행 엔진

### 1.1 프레임

사용자 코드는 `<iframe sandbox="allow-scripts">` 안에서 `srcdoc` 으로 실행된다. `allow-same-origin` 은 **절대 넣지 않는다.** 넣는 순간 부모 DOM 과 스토리지가 열린다. `allow-forms` 도 `allow-popups` 도 넣지 않는다.

그 대가로 프레임은 opaque origin(`origin === "null"`, `href === "about:srcdoc"`)이 되고 다음이 막힌다. 전부 실측이다.

| 막히는 것 | 증상 | 우회 |
|---|---|---|
| 로컬 `fetch` | `TypeError: Failed to fetch` (배포판은 CORS `*` 라 통과) | 레슨 `env` 의 가짜 `fetch` |
| 폼 기본 제출 | **`submit` 이벤트가 아예 발생하지 않는다** | `env` 가 `submit` 을 대신 쏜다 |
| `history.pushState`/`replaceState` | `SecurityError` (해시만 바꿔도) | `location.hash` 대입은 동작 |
| 해시 링크 클릭 | 프레임이 `about:srcdoc#…` 로 떠나 **빈 문서가 된다** | `env` 가 가로채 `location.hash` 만 바꾼다 |
| 그 밖의 링크 | — | 프렐류드가 막고 콘솔에 한 줄 남긴다 |

`react-router` 는 쓸 수 없다. `about:srcdoc` 이 유효한 base URL 이 아니라 `new URL()` 단계에서 `TypeError: Failed to construct 'URL': Invalid URL` 로 죽는다.

### 1.2 srcdoc 주입 순서

`js/frame-doc.js` 의 `buildHead` 가 조립한다. 순서가 곧 계약이다.

```
<!doctype html><html><head>
  <style> 테마 토큰 + 기본 스타일 </style>   ← 미리보기가 켜진 단계만
  <style> 레슨 scaffold.css </style>          ← 있을 때만
</head><body>
  레슨 scaffold.html                          ← 있을 때만. 사용자 코드보다 먼저 DOM 에 있어야 한다
  <script> 프렐류드 + assert 런타임 </script>
  <script> 레슨 env </script>                 ← 있을 때만. 프렐류드 뒤라 console 을 쓸 수 있다
  <script> React UMD </script>                ← runtime: 'react' 일 때만
  <script>
    사용자 코드                                 ← 여기부터 1행
  </script>
  <script> assert 실행 </script>              ← 검사가 있는 단계만
  <script> __assertsPromise 를 기다린 뒤 __done() </script>
</body></html>
```

프레임은 `srcdoc` 을 **먼저 넣고 나서** 부모에 붙인다. 순서를 바꾸면 초기 `about:blank` 로드가 `load` 를 먼저 때려 판정이 무너진다.

### 1.3 부모↔프레임 통신

`postMessage` 로만 오간다. opaque origin 이라 `event.origin` 은 언제나 `"null"` 이므로 **신뢰 판정은 `event.source === frame.contentWindow` 동일성으로** 한다.

| 메시지 | 방향 | 뜻 |
|---|---|---|
| `ping` | 자식 → 부모 | 살아 있다 (500ms 간격 설정) |
| `console` | 자식 → 부모 | `console.*` 미러 |
| `error` | 자식 → 부모 | `window.onerror` · 잡히지 않은 거부 |
| `assert` | 자식 → 부모 | 검사 한 건의 결과 |
| `done` | 자식 → 부모 | 스크립트와 검사가 끝났다 |

### 1.4 워치독 — 3갈래 판정

`js/runner.js`. 마지막 `ping` 이후 **3,000ms** 가 지나면 멈춘 것으로 본다. 부모가 500ms 마다 검사한다.

```
doneSeen            → 'async'    이미 끝났는데 비동기 콜백이 멈춰 있다
loadSeen && !ping   → 'startup'  프레임은 떴는데 프렐류드가 돌지 못했다
그 밖                → 'sync'     동기 무한 루프
```

`ping` 하나로는 갈리지 않는다. 블로킹 중에는 메시지 전달이 플러시되지 않아 무한 루프와 시작 실패가 **둘 다 ping 0건**으로 보이기 때문이다. `load` 를 함께 봐야 갈린다.

**탭이 숨겨져 있으면 검사를 건너뛴다.** 실측상 배경 탭에서는 브라우저가 타이머를 1초로 고정한다 — 설정 500ms 대비 **중앙값 1,000ms(범위 996~1,009ms)** 이고, 이 값은 프레임 크기와 무관하다(0×0 과 833×234 가 같다). 다시 보이는 순간 `lastPingAt` 을 리시드해 묵은 값으로 즉사시키지 않는다.

### 1.5 줄 번호 보정

`window.onerror` 의 `lineno` 는 srcdoc 문서 기준이다. 사용자 코드 1행 앞의 줄 수를 빼야 학습자의 편집기 줄 번호와 맞는다.

`offsetOf(head)` 가 **실행 시점에** 최종 head 의 줄 수를 센다. scaffold·env·React 가 레슨마다 달라 상수로 둘 수 없다. React 를 넣으면 앞이 300줄 넘게 늘어나는데 같은 함수가 자동으로 흡수한다.

### 1.6 실행 실패 마감

프레임을 띄우지도 못한 경우(JSX 변환 실패, React 로드 실패)에는 `window.onerror` 가 잡지 못한다. 부모가 같은 모양의 `error` + `done`(`started: false`)을 **합성해** 보낸다. 그렇게 하지 않으면 세션이 "실행 중" 에서 마감되지 않는다.

## 2. 검사 체계

`js/validator.js`. 검사기는 프레임 **안**에서 돈다. 비교와 표시 문자열 생성까지 안에서 끝내 함수·순환 참조가 부모로 넘어오지 못하게 한다(구조화 복제).

### 2.1 `value` assert

```json
{ "type": "value", "label": "…", "args": [1, 2], "expected": [2, 4] }
```

- 읽는 대상은 **`entry` 로 지정한 함수의 반환값**이다. 마지막 표현식이 아니다 — 학습자가 디버깅용 `console.log` 를 붙이면 완료값이 바뀌고, 완료값을 얻으려면 `eval` 이 필요해 줄 번호 정확도가 무너진다.
- `entry` 는 유효한 식별자여야 한다. `const`/`class` 로 선언한 것은 `window` 에 붙지 않으므로 식별자를 그대로 적어 렉시컬 스코프에서 찾는다.
- `args` 를 펼쳐 호출하고 `expected` 와 깊은 비교한다.
- **반환값이 thenable 이면 기다린다.** T5 이후의 비동기 레슨이 여기 기댄다.

### 2.2 `dom` assert

```json
{ "type": "dom", "label": "…", "select": ".course", "count": 3 }
{ "type": "dom", "label": "…", "select": ".state", "text": ["코스 3개"] }
{ "type": "dom", "label": "…", "select": ".result",
  "actions": [{ "action": "fill", "selector": "#title", "value": "리액트 입문" },
              { "action": "click", "selector": ".go" }] }
```

- `count` 를 주면 개수를, `text` 를 주면 보이는 글자 배열을 비교한다.
- 폼 컨트롤은 타이핑한 값이 `textContent` 에 없으므로 `value` 를 읽는다.
- **속성 선택자가 동작한다.** `[aria-invalid="true"]` 로 접근성 표시를 셀 수 있다. `:focus` 는 쓸 수 없다.
- 액션 대상이 없으면 `fail` 이 아니라 `error` 다. 학습자가 볼 곳이 다르다.

### 2.3 액션과 React 제어 컴포넌트

`fill` 은 `node.value = x` 로 넣지 않는다. React 는 폼 요소의 `value` 세터를 인스턴스에 덮어써 값 추적기를 함께 갱신하므로, 그대로 넣으면 뒤이은 `input` 이벤트를 "바뀐 것이 없다" 로 보아 `onChange` 를 부르지 않는다. **프로토타입의 원래 세터를 꺼내 호출한다.**

체크박스는 `fill` 이 `value` 를 건드리므로 `click` 으로 토글한다.

### 2.4 비동기 대응

각 액션 뒤와 첫 검사 전에 `settle()` 로 양보한다.

```
runtime: 'js'      마이크로태스크 1회
runtime: 'react'   MessageChannel 매크로태스크 2회
```

React 는 렌더 커밋과 효과 실행이 서로 다른 매크로태스크에 실린다. 실측: **양보 1회 → 화면은 그려졌지만 `useEffect` 는 아직, 2회 → 효과까지 끝남.** `setTimeout` 을 쓰지 않는 이유는 배경 탭에서 1초로 조여지기 때문이다. `MessageChannel` 은 그 대상이 아니고 React 스케줄러가 쓰는 통로라 우리 메시지가 렌더 뒤에 도착한다.

**두 번 양보는 효과 한 겹까지만 보장한다.** 효과가 상태를 바꿔 또 다른 효과를 부르는 레슨은 이 경로로 판정할 수 없다.

응답을 기다려야 하는 레슨은 검사용 함수를 starter 에 **보이게** 두고 `value` assert 의 진입으로 쓴다. 로딩 문구가 나타났다가 사라질 때까지 폴링하는 두 단계 대기다. 한 단계면 앞 검사가 남긴 화면을 읽는다.

### 2.5 타임아웃

`ASYNC_TIMEOUT_MS = 5000`. 진입 함수가 돌려준 thenable 이 그 안에 끝나지 않으면 그 검사만 `error` 로 끊는다. 영영 resolve 되지 않는 Promise 는 ping 이 계속 흐르므로 워치독이 잡지 못한다.

M2 에서 2,000ms 로 정했다가 T5 에서 올렸다. 그때 상정한 것은 Promise 하나였고, T5 는 **순차 요청이 레슨 내용**이라 전제가 깨졌다. 배경 탭에서는 요청당 약 1초가 되어(실측: 순차 1건 505ms · 2건 1,927ms · 3건 2,919ms · 4건 3,925ms) 옛 한도에서 3건이 넘겼다. 레슨 설계는 **검사당 순차 요청 3~4건 이내**로 잡는다.

### 2.6 검사로 강제할 수 없는 것

결과만 볼 수 있고 작성 형태는 볼 수 없다. 아래는 다른 형태로 써도 통과하며, 그 사실을 해당 레슨 지문에 밝혀 두었다.

`t1-02` 클로저 · `t2-06` 이벤트 위임 · `t5-05` `async`/`await` · `t5-11` `Promise.all` · `t5-13` 병렬 묶기 · `t6-03` 상태 하나로 묶기

## 3. 레슨 스키마

`schemaVersion: 2`. `js/lessons.js` 가 로드 시 정규화한다. v1(단계 없는 단일 `write`)은 자동으로 감싸 v2 모양으로 만든다.

### 3.1 레슨 레벨

| 필드 | 필수 | 뜻 |
|---|---|---|
| `schemaVersion` | ✔ | `2`(또는 v1) 이외는 로드 거부 |
| `id` | ✔ | 파일명과 일치해야 한다. 순번을 읽어 `order` 와 대조한다 |
| `track` · `order` · `title` | ✔ | 목록과 정렬 |
| `runtime` | — | `'js'`(기본) 또는 `'react'`. **`'react'` 인 레슨만** Babel 과 React 를 받는다 |
| `steps[]` | ✔ | 아래 |

### 3.2 단계 레벨

| 필드 | 필수 | 뜻 |
|---|---|---|
| `kind` | ✔ | `read`·`run`·`tweak`·`fill`·`write` |
| `title` · `brief` | ✔ | `brief` 는 **문단 배열**. `textContent` 로 그린다(마크다운 없음, `innerHTML` 없음) |
| `code` | `read` 외 ✔ | 편집기의 처음 내용 |
| `entry` | `value` assert 가 있으면 ✔ | 진입 함수 이름 |
| `solutionCode` | 검사 단계 ✔ | 정답 보기 · 검증용 |
| `asserts[]` | — | 없으면 실행만 하고 판정하지 않는다 |
| `scaffold` | — | `{ html, css }` — **학습자가 조작할 무대** |
| `env` | — | **환경**. 사용자 코드보다 먼저 도는 `<script>` |

### 3.3 `scaffold` 와 `env` 의 구분

| | `scaffold` | `env` |
|---|---|---|
| 무엇인가 | 학습자가 조작할 **무대**. 코드가 손댈 DOM 과 그 스타일 | **환경.** 그 레슨에서 세상이 어떻게 동작하는지 |
| 예 | 상품 카드, 검색 폼, `#root` | 가짜 `fetch`, 폼 제출 장치, 해시 링크 장치 |
| 보이는가 | 미리보기 패널에 보인다 | 보이지 않는다. `read` 지문이 밝힌다 |
| 주입 위치 | 사용자 코드 앞의 **본문** | 프렐류드 **뒤**, 사용자 코드 **앞** |

**미리보기 패널은 `scaffold.html` 유무로 켜진다.** 무대가 무대만 담으면 그 등식이 성립한다. 환경을 같은 필드에 섞으면 그릴 것이 없는 레슨에서 빈 패널이 열린다. 그래서 판정 코드를 고치는 대신 데이터를 갈랐다.

`env` 는 있을 때만 주입한다. 없으면 head 는 한 글자도 달라지지 않는다(335단계 전후 비교로 확인).

### 3.4 무대 장치를 쓰는 곳

전부 실행 틀의 제약을 메우는 것이고, **학습자 코드는 실무와 같다.** 해당 레슨 `read` 가 장치의 존재를 밝힌다.

| 장치 | 쓰는 트랙 | 학습자가 쓰는 것 |
|---|---|---|
| 가짜 `fetch` | T5 8레슨 · T6 전 레슨 | `fetch(url)` 그대로 |
| 폼 제출 | T6 4레슨 | `<form onSubmit>` + `preventDefault` |
| 해시 링크 | T6 4레슨 | `<a href="#/courses">` 그대로 |

`const { useState } = React;` 도 같은 성격의 무대 장치다. UMD 에는 훅이 전역에 없어 `React.useState` 로 써야 하는데, 실무의 `import { useState } from 'react'` 와 형태가 달라 그대로 두면 T8 에서 혼란이 남는다. `t4-01` read 가 이 제약과 이유를 밝힌다.

## 4. 단계 구조

한 레슨은 단계 여러 개로 이뤄진다. 종류는 다섯이고 화면 구성과 완료 조건이 종류로 정해진다(`js/steps.js`).

| 종류 | 화면 이름 | 편집기 | 실행 | 검사 패널 | 완료 조건 | 현재 개수 |
|---|---|---|---|---|---|---:|
| `read` | 읽기 | — | — | — | 언제나 참 (읽었는지는 관측할 수 없다) | 105 |
| `run` | 실행 | ✔ | ✔ | — | 한 번 실행하면 | 95 |
| `tweak` | 바꾸기 | ✔ | ✔ | — | **고쳐서** 실행하면 | 99 |
| `fill` | 채우기 | ✔ | ✔ | ✔ | 검사 전부 통과 | 102 |
| `write` | 쓰기 | ✔ | ✔ | ✔ | 검사 전부 통과 | 101 |

- 통과·실패가 없는 단계에 빈 검사 패널을 띄우지 않는다. 학습자가 자기가 뭘 놓쳤다고 생각한다.
- **완료는 관문이 아니라 기록이다.** 이동은 언제나 자유롭다.
- 되돌리기 버튼은 단계 종류가 아니라 **편집기가 있는지**로 정한다 — 고칠 수 있는 곳이면 되돌릴 수도 있어야 한다. 무한 루프를 넣고 빠져나올 길이 없으면 안 된다.
- 화면에는 우리말 이름만 보인다. 아무것도 모르는 상태로 시작하는 학습자에게 영어 단어 다섯 개가 먼저 보이면 그것부터 장벽이 된다.

## 5. 저장

`localStorage` 키 하나(`js-playground:v1`)에 전체 상태를 담는다.

```
{
  schemaVersion: 1,
  revision: 2,
  lastLessonId: 't6-14',
  lastStepIndex: 4,
  lessons: {
    't6-14': { steps: { 4: { code: '…', codeHash: 'a1b2c3d4', completedAt, updatedAt } } }
  },
  settings: { theme: 'dark' }
}
```

### 5.1 서명 기반 무효화

레슨의 starter 코드가 바뀌면 저장해 둔 코드는 남의 코드가 된다. 그렇다고 원문을 저장에 끌고 들어갈 수는 없다.

**FNV-1a 32비트 해시**로 서명한다. 저장할 때 그 단계의 starter 해시를 함께 적고, 불러올 때 지금 starter 의 해시와 비교한다.

```
saved.codeHash === 지금 starter 해시   → 저장분을 쓴다 (이어하기)
다르고 저장분이 자기 서명과 맞음        → starter 가 바뀐 것이다. 새 starter 를 쓴다
```

### 5.2 개정 번호

`REVISION`. 레슨이 다른 번호로 옮겨 가면 옛 저장분이 남의 레슨에 붙는다. 번호를 올리면 **그 회차에 옮긴 트랙의 저장분만** 버리고 다른 트랙 진행 상황은 남긴다. 현재 값은 2이고, T1 재분할 때 `t1-*` 을 한 번 비웠다.

### 5.3 실패해도 학습은 계속된다

손상된 JSON 도, 프라이빗 모드의 예외도 결말은 같다. 빈 상태로 시작하고 학습을 막지 않는다.

## 6. 화면

### 6.1 구성

상단 바(레슨 메뉴 · 테마 토글) · 단계 칩 · 지문 패널 · 편집기 · 미리보기 · 콘솔/검사 결과 · 다음 단계.

### 6.2 반응형 3구간

| 구간 | 배치 | 실측 (대표 폭) |
|---|---|---|
| **≥1280** | 지문 · 편집기 · 미리보기 3분할 | 1440px 에서 384 / 528 / 528 |
| **768~1279** | 지문 위, 편집기·미리보기 아래 | 1024px 에서 608 / 420 / 420 |
| **<768** | 지문만. **편집기와 미리보기를 내린다** | 390px 에서 358 |

`<768` 에서 편집기를 내리는 것은 설계다. 좁은 화면에서 코드 편집은 학습을 방해한다. 세 구간 모두 **가로 스크롤 0건**이다(긴 코드 토큰 14건이 있는 단계를 390px 에서 전수 확인).

### 6.3 진행 표시

트랙별 완료 개수와 현재 위치를 상단에 표시한다. 완료는 기록이므로 잠그지 않는다.

### 6.4 레슨 목록 오버레이

`role="dialog"` · `aria-modal="true"`. **포커스 트랩이 동작한다**(실측: 진짜 키 입력으로 확인).

트랙 제목은 `aria-expanded`와 `aria-controls`를 가진 아코디언 버튼이다. 한 번에 트랙 하나만 펼치며, 메뉴를 열 때 현재 레슨이 속한 트랙을 자동으로 펼치고 현재 레슨 링크로 이동한다. 각 제목 옆에는 해당 트랙의 레슨 수를 표시한다.

```
Enter 로 열면   현재 레슨 링크로 포커스가 들어간다
Tab 10회        10회 뒤에도 오버레이 안에 머문다
Shift+Tab       역방향도 안쪽에 머문다
Escape          닫히고 포커스가 여는 버튼으로 돌아온다
```

### 6.5 키보드

```
Tab 순서       건너뛰기 링크 → 레슨 메뉴 → 단계 칩 → 테마 토글 → 다음 단계
편집기         그냥 Tab 은 들여쓰기 · Esc 를 누른 뒤 Tab 이면 실행 버튼으로 나간다
```

CodeMirror 는 `Tab` 을 들여쓰기로 먹어 포커스 트랩을 만든다. `Escape` 를 누르면 다음 `Tab` 한 번만 브라우저 기본 동작(포커스 이동)을 살린다. `Shift-Tab` 도 같다.

단계 칩과 레슨 목록 항목은 전부 `<button>` 이고 `tabindex` 를 손대지 않았다. 건너뛰기 링크는 `#main` 을 가리킨다.

### 6.6 테마

2단 토큰(primitive → semantic). 컴포넌트는 semantic 만 참조한다. `css/` 의 하드코딩 색상 **0건**, `!important` **0건**.

고르지 않았으면 `data-theme` 을 비워 `prefers-color-scheme` 이 그대로 작동한다. 고르면 `data-theme="dark|light"` 가 그것을 이긴다. 선택은 `settings` 에 저장된다.

프레임은 별도 문서라 부모의 CSS 변수가 상속되지 않는다. 미리보기가 켜진 단계에서는 **부모의 계산된 토큰 값을 읽어 프레임에 넘긴다.** 그렇게 하지 않으면 다크 모드에서 미리보기만 흰 판으로 남는다.

## 7. 트랜스파일과 React

### 7.1 언제 받는가

`runtime: 'react'` 인 레슨을 실행할 때 **처음으로** 받는다. `js` 레슨에서는 요청이 **0건**이다(동적 `import` 로 분리).

### 7.2 무엇을 받는가

| 대상 | 주소 | 비고 |
|---|---|---|
| 트랜스파일러 | `@babel/standalone@7.26.4` (esm.sh) | `presets: [['react', { runtime: 'classic' }]]` |
| React | `react@18.3.1` / `react-dom@18.3.1` UMD **개발 빌드** | 실측 +1,023KB · +118ms |

### 7.3 `retainLines`

줄 번호를 지키는 유일한 장치다. 빼면 변환 결과의 줄이 밀려 `runner` 의 줄 번호 보정이 무의미해진다. `sourceType: 'script'` 로 두는 이유는 실제로 classic script 로 넣기 때문이다.

### 7.4 개발 빌드를 쓰는 이유

production 빌드에서는 `class` 를 써도 `className` 과 결과가 **완전히 같다.** DOM 의 class 속성도, 스타일도, 콘솔도 같다. **잘못을 알 방법이 아예 없다.** 트랜스파일러 셋도 React 런타임도 이것을 잡지 못한다(실측).

그리고 `key` 누락 · 훅 규칙 위반 · 조건부 훅 호출 경고가 **전부 개발 빌드 전용**이다. T4 가 그 경고 위에 서 있다.

### 7.5 실패 경로

Babel 이나 React 를 받지 못하면 폴백하지 않는다. 대체할 것이 없다. 대신 **명확한 안내로 끝낸다** — 부모가 `error` + `done`(`started: false`, `blocked: true`)을 합성해 "실행 준비가 되지 않아 검사하지 못했습니다" 로 마감한다. 코드 오류로 인한 실패와 문구가 갈린다.

## 8. 다중 파일 실행 (`files[]`)

한 단계가 여러 파일로 이루어지고 학습자가 `import`/`export` 로 잇는다. `files[]` 가 있는 단계만 이 경로를 탄다. 없는 단계의 조립은 한 바이트도 달라지지 않는다(502단계 전수 확인).

### 8.1 blob 을 프레임 안에서 만드는 이유

blob URL 은 만든 문서의 출처에 묶인다. 부모(http)가 만든 blob 을 opaque origin 프레임이 가져오려 하면 실패한다(실측). 그래서 URL 생성은 프레임 안에서 한다. 프레임이 문서로 들어오기 전에는 URL 이 없으므로 모듈 스크립트를 **파서가 삽입할 수 없다.** 프레임 안 classic 부트스트랩이 동적으로 붙인다.

### 8.1.1 지정자를 URL 로 바꾸지 않고 import map 에 맡기는 이유

blob 의 **내용은 만드는 순간 굳고** URL 은 그전에 알 수 없다. 지정자에 상대 URL 을 박아 넣는 방식으로는 서로를 부르는 두 파일을 **만들 수조차 없다** — 순환이 원리적으로 불가능해진다.

이름은 blob 이 생기기 전에 이미 정해져 있다. 그래서 `'./이름'` 에서 `./` 만 떼고, 이름 → blob URL 의 import map 을 프레임 안에서 심는다. 부수 효과로 **파일 순서가 의미를 잃는다** — 위상 정렬이 필요 없다.

### 8.2 조립 순서

```
<style> 테마 · scaffold.css
scaffold.html
<script> 프렐류드 + assert 런타임
<script> env
<script> 모듈 로더
<script> window.__pgStart({files, entry, check, specs, react})
         ├ 파일마다 blob 생성
         ├ <script type="importmap"> {이름: blob URL} 삽입 (모듈이 뜨기 전이어야 한다)
         └ <script type="module"> 부트 삽입
<script> done — __assertsPromise 를 기다린다
```

로더는 파일마다 blob 을 만들고 import map 을 심은 뒤, `import * as ns` 로 진입 네임스페이스를 `window.__pgEntry` 에 담는 **부트 모듈**을 `<script type="module">` 로 붙인다. 진입 파일도 이름으로 부른다 — import map 이 푼다. 검사기는 전역이 아니라 그 네임스페이스에서 진입 함수를 찾는다 — 모듈 안의 `export` 는 `window` 에 붙지 않는다.

### 8.3 실패 마감

요소의 `load` 는 성공 신호가 아니라 **마감 신호**다. 문법 오류든 최상위 `throw` 든 2~3ms 안에 온다(실측). `load` 가 왔는데 부트가 `__pgModuleReady` 를 부르지 않았으면 실패다. 워치독 3초를 기다리지 않는다. 요소의 `error` 는 파싱 실패가 아니라 **가져오기 실패에만** 온다.

파일을 못 불러온 경우에는 assert 를 돌리지 않고 전부 오류로 마감한다. 돌려 봐야 엉뚱한 실패만 쌓인다.

### 8.4 줄 번호

각 파일이 제 blob 이라 `window.onerror` 의 줄·열이 **이미 파일 기준**이다. `offsetOf` 보정을 하지 않는다(`lineOffset = 0`). 오류의 `filename`(blob URL)은 프렐류드가 파일 이름으로 옮긴다. 링크 오류 본문에 실려 오는 blob URL 도 같이 옮긴다.

Babel 로 미리 파싱하지 않는다. 콜드 로드 650ms 를 내고 얻을 것이 없다 — `<script type="module">` 로 붙이는 것만으로 파일·줄·열이 전부 나온다.

### 8.5 지정자 재작성의 한계

지정자 추출이 **정규식**이다. `from '…'` 와 `import '…'`/`import('…')` 뒤의 문자열 리터럴을 찾아, 같은 리터럴에서 `./` 를 뗀다. 그래서 **문자열 안의 문자열도 바뀐다.**

```js
const 안내 = "from './utils.js' 라고 적으세요";  // 이 문자열도 재작성된다
```

진짜 파서를 쓰면 막을 수 있지만 그러려면 Babel 이 필요하고, §8.4 의 이유로 쓰지 않기로 했다. 대신 **T8 레슨 소재에 그런 코드를 넣지 않는다.** 지정자 모양의 문자열을 본문에 담는 레슨을 만들지 않는다.

### 8.6 지정자 규칙

`'./이름.js'` 한 가지만 받는다. 하위 디렉터리를 두지 않으므로 해석이 한 단계로 끝난다. 상위 폴더(`../`)·절대 경로(`/`)·맨 지정자(`'lodash'`)는 각각 다른 문구로 거절한다 — 학습자가 고칠 곳이 다르다. import map 은 쓰지 않는다.

**순환은 막지 않는다.** 실제 ES 모듈의 거동이 그대로 드러나고 그것이 `t8-08` 의 교재다. 실측:

```
나중에 부르는 함수로 읽으면      정상 동작
최상위에서 즉시 읽으면            utils.js 2행
                                  ReferenceError: Cannot access 'factor' before initialization
```

### 8.7 진입 함수를 못 찾은 이유

한 문구로 뭉개지 않는다. 고칠 곳이 경우마다 다르다.

| 상태 | 학습자가 고칠 것 |
|---|---|
| 파일을 못 불러왔다 | 그 파일 그 행의 오류 (파일·행을 문구에 넣는다) |
| 네임스페이스가 비었다 | `export` 를 붙인다 |
| 그 이름만 없다 | 이름을 맞춘다 (지금 내보내는 이름들을 보여 준다) |
| `export default` 로 내보냈다 | 이름 있는 `export` 로 바꾼다 |
| 내보냈는데 함수가 아니다 | 함수를 내보낸다 (지금 무엇인지 밝힌다) |

### 8.8 `files[]` 스키마

단계 수준에 둔다. 한 레슨 안에서도 단계마다 파일 구성이 다르기 때문이다.

```json
{
  "kind": "write",
  "entry": "doubleAll",
  "files": [
    { "name": "main.js", "entry": true,
      "code": ["…"], "solutionCode": ["…"] },
    { "name": "utils.js", "readOnly": true, "code": ["…"] }
  ]
}
```

| 필드 | 규칙 |
|---|---|
| `name` | 파일 이름. 지정자 해석의 키. 중복 금지. `/^[A-Za-z0-9_-]+\.js$/` — 하위 디렉터리 없음 |
| `entry` | **정확히 하나**의 파일에 `true`. 이 파일부터 불러온다 |
| `code` · `solutionCode` | 파일별. 줄 배열 또는 문자열 |
| `readOnly` | 참고 파일. 편집기에서 잠그고 저장하지 않는다. `solutionCode` 를 둘 수 없다 |
| 순서 | **배열 순서가 곧 탭 순서.** 순서 필드를 따로 두지 않는다 |

**`entry` 라는 단어가 두 층에서 다른 뜻이다.** 파일의 `entry` 는 "어느 파일부터 불러오는가", 단계의 `entry` 는 "그 파일에서 무엇을 검사하는가"다. 층이 다르므로 이름을 바꾸지 않았다. 검사기는 전역이 아니라 **진입 모듈의 네임스페이스**에서 단계의 `entry` 를 찾는다 — 모듈 안의 `export` 는 `window` 에 붙지 않는다.

### 8.9 실행 순서 — 부트 모듈

로더(`__pgStart`)가 한 번에 하는 일이다. 전부 동기다.

1. 파일마다 blob 을 만들고 `이름 → URL` 표를 세운다
2. 오류의 파일 이름 표를 프렐류드에 넘긴다(`rt.setFiles`)
3. `<script type="importmap">` 을 심는다 — **모듈이 하나라도 뜨기 전이어야 한다**
4. `window.__assertsPromise` 에 아직 풀리지 않은 약속을 건다
5. 부트 모듈을 blob 으로 만들어 `<script type="module">` 로 붙인다

부트 모듈은 세 줄이다.

```js
import * as ns from 'main.js';   // 진입 파일도 이름으로 부른다. import map 이 푼다
window.__pgEntry = ns;
window.__pgModuleReady();
```

`__pgModuleReady` 는 **모듈 평가 도중에** 불린다 — 요소의 `load` 보다 먼저다. 그것이 검사를 돌리고 `__assertsPromise` 를 푼다. 문서 끝의 `done` 스크립트는 그 약속을 기다린다 — `files[]` 가 없는 단계와 **같은 계약**이다.

`load` 가 왔는데 `__pgModuleReady` 가 불리지 않았으면 실패로 마감한다(§8.3).

### 8.10 파일 탭

편집기는 **`EditorView` 하나**에 파일마다 `EditorState` 를 바꿔 끼운다. 인스턴스를 파일 수만큼 만들지 않는다. 실측:

```
뷰 3개 생성            13 / 6 / 4ms · 합 23ms · DOM +325개
뷰 1개 + 상태 3개       상태 1/1/1ms · 뷰 3ms · DOM +108개
setState 전환 6회       0.4 ~ 1.1ms
전환 뒤 돌아왔을 때      문서 같음 · 커서 25→25 같음 · 실행 취소 동작
```

"하나를 쓰면 실행 취소 이력과 커서가 날아간다" 는 **`setValue` 로 바꿔 끼울 때만** 참이다. CodeMirror 6 는 이력과 선택 영역을 `EditorState` 에 담으므로 파일별 상태를 물면 둘 다 남는다.

**결정적인 이유는 F-008 이다.** `createEditor` 가 비동기라 취소 경로가 필요한데, 지금 세대 번호는 마운트가 하나라는 전제 위에 있다. 인스턴스가 N 개면 진행 중인 비동기 마운트도 취소 경로도 N 개가 된다.

탭 요소는 `index.html` 에 두지 않고 **필요할 때 만들었다 지운다.** `hidden` 으로 숨겨 두면 보이지 않아도 `files[]` 없는 단계의 DOM 이 달라진다. `<768` 에서는 편집기를 만들지 않으므로 탭도 만들지 않고 파일을 세로로 잇는다.

### 8.11 저장

파일별로 나눈다 — `steps[i].files['main.js'] = { code, codeHash }`. 합치면 ① 파일을 잇는 구분자를 학습자 코드가 담을 수 있고 ② 한 파일의 starter 만 고쳐도 전부 날아가며 ③ 파일이 하나 늘면 옛 저장분을 어디에 붙일지 알 수 없다.

`codeHash` 는 **파일별 starter 의 서명**이라 한 파일의 예제 코드만 바뀌면 그 파일만 초기화된다. `readOnly` 파일은 저장하지 않는다 — 학습자가 고칠 수 없어 저장할 것이 없고 레슨 데이터가 이긴다.

되돌리기는 상태를 새로 만들지 않고 **문서를 치환**한다. 코드 한 벌 단계의 되돌리기와 같은 동작이어야 하고, 지금 동작은 되돌린 뒤 실행 취소로 되살릴 수 있다.

`SCHEMA_VERSION` 도 `REVISION` 도 올리지 않는다 — `files` 는 새 키이고 기존 단계의 모양은 그대로다.

### 8.12 금지 조합

- `files` 와 `code`/`solutionCode` 병기 → 레슨 로드에서 거절. 어느 쪽이 이기는지 규칙을 만들면 반드시 틀린다.

`runtime: 'react'` + `files` 는 **열려 있다.** Babel 을 `sourceType: 'module'` 로 돌려도 `import`/`export` 가 통과하고 `retainLines` 가 줄 수를 지키며, UMD React 는 classic script 로 먼저 들어가 모듈 스코프에서 전역으로 보인다(실측). 파일마다 변환하고, 변환에 실패하면 어느 파일인지 문구에 붙인다.

`read` 단계에는 `files` 를 두지 않는다. `read` 는 에디터 pane 이 숨겨져 파일이 보이지 않는다.

## 9. 앞 단계 코드 · 힌트 · 정답 보기

### 9.0 앞 단계 코드 (F-19)

단계를 옮기면 편집기 내용이 그 단계 것으로 바뀐다. 앞에서 본 코드를 다시 보려면 지금 쓰던 것을 두고 돌아가야 했다. `fill`·`write` 에서 **같은 레슨의 가장 가까운 앞 단계 코드**를 접었다 펼친다.

**실패를 조건으로 걸지 않는다.** 막혀서 주는 도움이 아니라 화면 구조의 결손을 메우는 것이므로 처음부터 보인다.

**무엇을 보여주는가** — `solutionCode` 가 있으면 그것, 없으면 `code` 다. `fill` 은 빈칸이 아니라 **채워진 모습**이어야 한다. 학습자가 기억하려는 것은 자기가 완성한 판이지 빈칸이 뚫린 판이 아니다. `tweak`·`run` 은 `solutionCode` 가 없으므로 그대로 동작하는 예제가 나온다. `files[]` 단계는 파일마다 이름을 머리에 달아 잇는다.

**학습자가 저장한 코드는 쓰지 않는다.** `tweak` 은 일부러 망가뜨리라고 시킨 자리라, 저장분을 보여 주면 깨진 코드를 참고 자료로 내놓게 된다.

**같은 레슨 안으로 제한한다.** 레슨 경계를 넘으면 무엇을 보여줄지 규칙이 무너진다. 레슨 간 왕복은 레슨 목록이 맡는다.

**자동으로 고른다.** 저자가 레슨마다 참조 단계를 따로 지정하지 않는다. 앱이 같은 레슨 안에서 코드가 있는 가장 가까운 앞 단계를 찾는다. 현재 283레슨에도 같은 규칙을 적용한다.

**버튼 라벨은 칩 이름을 그대로 쓴다** — `4 채우기 단계 코드 보기`. 학습자가 위에서 보고 있는 그 칩이어야 헷갈리지 않는다.

### 9.1 힌트와 정답 보기

계단 하나다. 힌트가 먼저, 정답이 나중이다. `fill`·`write` 단계에만 나온다.

| | 힌트 (F-18) | 정답 보기 (F-11) |
|---|---|---|
| 언제 | **2회 실패 후** 버튼이 나타난다 | **4회 실패 후** |
| 무엇 | `hints[]` 를 하나씩 펼친다. 최대 2개 | `solutionCode` 를 펼쳐 보여 준다 |
| 편집기 | 손대지 않는다 | **손대지 않는다.** 옮겨 적는 것은 학습자의 선택이다 |

**처음부터 버튼을 보이지 않는다.** 이 도구의 `tweak` 단계는 직접 틀려 보는 것이 핵심이다. 실패가 학습 재료인 도구에서 힌트 버튼이 처음부터 옆에 있으면 실패 전에 눌린다. 1회 실패는 대개 오타이고 검사의 `기대`/`실제` 병기가 이미 답을 준다.

### 9.2 실패 횟수를 어디에 두는가

`sessionStorage` 에 `hint:<레슨>:<단계>` 로 둔다. 진행 데이터(`localStorage`)에 넣지 않는다.

- **진행 데이터에 넣으면** 어제 두 번 틀린 사람에게 오늘 처음부터 힌트가 보인다.
- **메모리에만 두면** 새로고침에 사라진다. 캐시 안내(§11)가 학습자에게 새로고침을 시키므로 도구가 두 번 방해하게 된다.
- `sessionStorage` 는 탭을 닫으면 비고 새로고침은 견딘다. 그 사이가 맞다.

통과한 실행은 세지 않는다. 막힌 횟수만 센다.

### 9.3 완료 처리와 지표

**완료를 막지 않는다.** 정답을 보고 통과해도 완료다 — 이 도구에서 완료는 관문이 아니라 기록이다.

대신 단계 기록에 **`revealedAt`** 을 남긴다. 정답을 처음 펼친 시각이다. **화면에는 아무 표시도 하지 않는다** — 칩도 진행률도 목록도 그대로다. 학습자를 벌주는 표시가 아니라 PRD §7.1 의 지표를 계산할 재료다.

```
T4 정답 보기 비율 = revealedAt 이 있는 T4 fill·write 단계 수
                  ÷ completedAt 이 있는 T4 fill·write 단계 수
```

### 9.4 힌트 문구의 기준

**"무엇을 쓰라" 가 아니라 "무엇을 확인하라" 다.** 읽고도 여전히 코드를 여러 줄 생각해야 하면 좋은 힌트다.

1. **식별자를 완성해 주지 않는다.** `product.price` 를 쓰지 않고 "위에 적힌 이름" 이라고 가리킨다.
2. **코드 조각은 그 단계의 답이 아닌 것만.** 문법 모양은 되고 정답 표현은 안 된다.
3. **질문으로 끝낸다.** 학습자가 자기 코드를 다시 읽게 만든다.

**쓰기 전에 그 단계를 starter 상태로 실행해 검사가 무엇을 말하는지 읽는다.** 검사가 이미 알려 주는 것(어느 선택자가 없는지, 기대와 실제가 무엇인지)을 힌트에 다시 쓰면 힌트가 무의미하다.

## 10. 배포와 버전

GitHub Actions 가 배포 시점에 커밋 해시를 `version.json` 과 `js/version.js` 에 주입한다. 앱은 캐시된 `BUILD` 와 `fetch('version.json', {cache:'no-store'})` 를 비교해 평소 콘솔 한 줄, 불일치일 때만 경고를 추가한다. UI 는 늘리지 않는다.

빌드 파이프라인은 없다. `package.json` 도 없다. 저장소를 그대로 정적 배포한다.
