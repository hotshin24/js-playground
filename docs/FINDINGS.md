### 부수 확인

- **샌드박스 격리:** iframe에서 `parent.document` → `SecurityError`, `localStorage` → `SecurityError`, `origin` → `null`. `sandbox` 속성값 `allow-scripts` 단독.
- **부모 응답성:** 6초 블로킹 루프 중에도 부모 페이지 정상 동작. Worker 전환 불필요.
- **좀비 프로세스 없음:** 강제 종료 후 16초간 `top` 4회 샘플링 — 100%에 붙은 렌더러 프로세스 없음. `frame.remove()`가 실제로 루프를 종료시킨다.
- **워치독 방어:** `clearInterval`/`clearTimeout` 래핑으로 타이머 id 무차별 해제(300회) 후에도 ping 유지. 실측 확인.

### 통과했으나 한계가 확인된 항목

블로킹 실행 중 발생한 `console.log`는 부모에 도달하지 않는다. → **F-006**

## 공통 원인 R-1 — 블로킹 중 크로스프로세스 전달 미플러시

F-003 과 F-006 은 별개 버그가 아니다. **같은 현상이 두 곳에서 드러난 것**이다. 원인은 여기 한 곳에만 적고, 두 항목은 이 절을 참조한다.

**현상** — 자식(sandbox iframe)이 `postMessage` 를 호출해도, 자식 메인 스레드가 이벤트 루프를 양보하기 전까지 부모에 전달되지 않는다. **호출이 늦는 것이 아니라 전달이 늦는다.**

**계측** — 프로덕션과 동일 조건(`sandbox="allow-scripts"`, srcdoc, script 태그 분리)의 프로브 프레임에서 자식의 호출 시각과 부모의 수신 시각을 분리 측정.

2초 블로킹:

```
A_prelude_sync   child=5ms      parent=2008ms   ← 호출 5ms, 도착 2008ms
B_microtask      child=5ms      parent=2008ms
D_after_block    child=2005ms   parent=2008ms
E_done_slot      child=2005ms   parent=2008ms
C_timeout0       child=2006ms   parent=2008ms
```

블로킹 없는 대조군은 전원 `child≈8ms / parent=18ms`.

**해석** — 프렐류드의 첫 ping 은 script 태그 파싱 시점에 **동기 실행된다**(자식 기준 5ms). 마이크로태스크도 타이머도 경유하지 않는다. 그럼에도 5건 전부 블로킹이 끝난 뒤 `parent=2008ms` 에 **일괄 도착**했다.

**따라야 하는 결론** — 자식이 보내는 어떤 신호도 블로킹 구간을 건너오지 못한다. 따라서 **자식 신호만으로는 "실행 중 멈춤"과 "프레임 시작 실패"를 구분할 수 없다**(둘 다 도착 0건). 부모가 직접 받는 신호(iframe `load`)를 함께 봐야 갈린다.

| 프레임 상태 | `load` | ping | 3초 시점 판정 |
|---|---|---|---|
| 정상 코드 | 19ms | 21ms | — |
| 3초 블로킹 | 3006ms (임계값 이후) | 3006ms | `!load && !ping` → 실행 중 멈춤 |
| 스크립트 실행 불가 프레임 | 10ms | 0건 | `load && !ping` → 시작 실패 |

러너가 실제로 만드는 iframe 에서도 재측정했다. 정상 코드 `load` 210ms, 4초 블로킹 `load` 4154ms — 초기 about:blank 로드가 `load` 를 앞당겨 때리는 일은 없다(srcdoc 를 붙이기 전에 넣는 순서 유지 조건).

## 미해결 항목

### F-001 프레임 단위 스로틀 오탐

- **증상** — 정상 동작 중인 프레임을 워치독이 죽일 수 있다. 자식의 ping 타이머가 브라우저에 의해 지연되면 부모는 이를 "멈춤"으로 오판한다.
- **재현 조건** — 실행 프레임이 0×0 크기 + opaque origin(`sandbox="allow-scripts"`, srcdoc)인 현재 구성. 크롬은 이런 프레임의 타이머에 프레임 단위로 개입하므로 **탭이 foreground여도 발생할 수 있다.** 현재까지 실제 오탐은 미관측.
- **판단** — 부모의 `document.hidden` 가드는 **탭 단위만** 커버한다. 프레임 단위 스로틀은 막지 못한다. 이 한계를 알고 현 구성을 유지한다.
- **관측 기록** — 사용자 브라우저(foreground 탭)에서 `setInterval(… , 1000)` **30초 관측: 오탐 종료 0건.** 현재 구성에서 실제 오탐은 아직 미관측.
- **처리 시점** — **미해결 유지.** 미리보기 프레임이 실제 크기로 화면에 붙은 뒤 재검증한다. 프레임이 보이는 상태에서도 오탐이 나면 그때 대응한다.

### F-002 ping 실측 간격이 설정값과 다름

- **증상** — 프렐류드는 500ms 간격으로 ping을 보내도록 설정돼 있으나, 실측 도착 간격은 약 830ms다. 원인 미확정.
- **재현 조건** — 테스트 A~E 진행 중 관측. 현재 구성에서 상시.
- **판단** — 임계값 3초 대비 여유가 설계 의도인 6회분이 아니라 **3회분**이다. ping 2회만 연속으로 밀려도 오탐 사정권에 들어간다. 지금 당장 깨지지는 않으므로 값은 유지한다.
- **관측 기록** — 30초 관측에서 오탐 0건. **임계값 상향은 아직 불필요.**
- **처리 시점** — **미해결 유지.** F-001 재검증에서 오탐이 1건이라도 관측되면 그때 임계값을 3초 → **5초**로 상향한다.

### F-003 워치독 안내 문구 분기

- **처리 상태** — **처리 완료** (커밋 `32428d6`). `pingSeen` 단독 판별을 제거하고 `load` 기준 3갈래로 교체했다. 사용자 브라우저(foreground 탭) 실측 확인: 동기 무한 루프와 비동기 콜백 멈춤의 안내 문구가 정확히 갈린다. startup 분기는 인위 재현 수단이 없어 미관측.
- **증상** — `console.log('시작'); while (true) {}` 실행 시 "실행 프레임이 3초 안에 시작하지 못했습니다"(startup 분기)가 떴다. 기대는 sync 분기. 2회 재현. 대조군(`console.log('시작')` 단독)은 정상.
- **재현 조건** — 동기 무한 루프 전체. 부모에게 아무 메시지도 도달하지 못한 채 3초를 넘기는 모든 경우.
- **판단** — `pingSeen` 판별식이 성립하지 않는다. **원인은 → 공통 원인 R-1.** 3초 시점에 "무한 루프"와 "프레임 시작 실패"가 둘 다 ping 0건이라 자식 신호만으로는 갈리지 않는다. 부모가 직접 받는 `load` 를 판별에 넣어 해결했다.
- **처리 시점** — 처리 완료.

### F-004 콘솔 로그 라인 수 상한 없음

- **처리 상태** — **처리 완료** (커밋 `20df4bd`). 200줄 출력 시 200개 전부 유지, 1500줄 출력 시 노드 1001개(안내 1 + 로그 1000)·앞 500줄 생략 표시·마지막 줄 보존을 실측 확인.
- **증상** — 부모 콘솔 패널에 쌓이는 `<li>` 노드에 상한이 없다. 대량 출력 시 DOM 노드가 무제한 증가한다.
- **재현 조건** — `while (true) console.log(1)`. 크롬은 견뎠으나 이는 우연이며 보장된 동작이 아니다.
- **판단** — 상한 **1000줄**을 두고 초과분은 앞에서 버린다(버린 사실은 표시).
- **처리 시점** — **M1.**

### F-005 `done`이 비동기 완료를 판정하지 못함

- **증상** — `done`은 동기 실행이 끝난 시점에만 발신된다. 실제 작업이 비동기인 코드는 아직 실행 중인데도 "동기 실행 완료"로 표시된다. 언제 결과를 검사해야 하는지 판단할 신호가 없다.
- **재현 조건** — `setTimeout(() => console.log('끝'), 500)` — `done`은 즉시 오고 로그는 그 뒤에 온다.
- **판단** — M0 범위에서는 의도된 축소다(`done` = 동기 실행 완료). 그러나 검증(assert)을 붙이려면 "실행이 끝났다"의 정의가 필요하다. 비동기 트랙에서는 이 신호 없이 통과/실패를 판정할 수 없다.
- **처리 시점** — **T1-8(비동기 트랙) 진입 전.** 그 전까지는 동기 레슨만 검증 대상으로 둔다.

### F-006 블로킹 중 `console.log` 미도달

- **처리 상태** — **처리 완료(완화)** (커밋 `20df4bd`). 사용자 브라우저 실측 확인: 강제 종료 안내에 "이 시점까지 도착한 로그만 표시됩니다"가 표시된다.
  **단, 원인 R-1 자체는 해결되지 않았다.** 블로킹 직전 로그는 여전히 도착하지 않으며, 학습자에게 그 사실을 알리는 것까지가 이 항목의 처리 범위다. 완화만 된 상태다.
- **증상** — 무한 루프에 빠지면 **그 이전에 찍은 로그도** 부모에 도달하지 않는다. 학습자는 강제 종료 안내만 보고 어디서 멈췄는지 알 수 없다.
- **재현 조건** — `console.log('시작')` 직후 `while (true) {}`. 6초 블로킹에서 도착 0건. 1초 블로킹 대조군에서는 루프 종료 후 일괄 도착.
  **트리거는 레슨 주제와 무관하다.** 무한 루프를 가르치는 레슨이 있느냐와 별개로, T1-5(조건·반복)에서 학습자가 증감 방향을 실수하면 바로 밟는다.
- **판단** — 유실이 아니라 **발신 지연**이다. **원인은 → 공통 원인 R-1.** 워치독이 프레임을 제거하면서 대기 중이던 큐가 함께 소멸한다. `allow-same-origin` 없이 쓸 수 있는 채널이 `postMessage` 뿐이라 근본 해결책이 없다. **해결이 아니라 완화 항목으로 둔다.**
- **처리 시점** — **M1.** 강제 종료 안내에 "이 시점까지 도착한 로그만 표시됩니다" 한 줄을 추가한다. 학습자가 도구를 의심하지 않게 하는 것이 목적이다.
