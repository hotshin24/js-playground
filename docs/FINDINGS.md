## M0 검증 완료 (2026-08-19)

M0의 4개 목표와 하트비트 워치독까지 전부 실측 통과했다.
**이전 보고에서 "워치독 강제 종료 미검증" 상태로 남겨둔 항목은 해소됐다.**

### 통과 항목

| 항목 | 결과 | 측정 환경 |
|---|---|---|
| textarea 코드 → sandbox iframe 실행 | 통과. `완료 (103ms)` / 배포본 `(142ms)` | Chromium, localhost + GitHub Pages |
| `console.log` → 부모 패널 미러링 | 통과. `{name: "호진", tags: ["js", "react"]}` 직렬화·warn 색 구분 동작 | 〃 |
| 런타임 에러 + 줄 번호 | 통과. ReferenceError `(3:1)`, SyntaxError `(2:11)`, throw `(2:3)` — srcdoc 오프셋 보정 정확 | 〃 |
| 동기 무한 루프 3초 강제 종료 | 통과. `while(true)` → 프레임 제거 + 안내 문구 | 〃 |
| 비동기 무한 루프 강제 종료 (워치독) | **통과.** 테스트 A~E 5건 전부 통과, 강제 종료 실측 확인 | foreground 탭 |

### 워치독 테스트 A~E (5건 전부 통과)

| 테스트 | 코드 | 기대 동작 |
|---|---|---|
| A | `setTimeout(() => { while(true){} }, 0)` | 동기 완료 후 약 3초 뒤 "비동기 콜백이…" 종료 |
| B | `while (true) {}` | 3초 뒤 "3초 안에 끝나지 않아…" 종료 (A와 문구 분리) |
| C | `for (i<500) clearInterval(i)` + 비동기 루프 | 워치독 생존, 정상 종료 |
| D | `setInterval(() => console.log('tick'), 1000)` | 오탐 없음. 계속 출력 |
| E | D 실행 후 탭 30초 이탈 → 복귀 | 복귀 직후 오탐 종료 없음 |

> **정의 변경 안내** — 이 절의 `done` 은 당시 정의인 "동기 실행 완료"를 가리킨다. 현재 `done` 은 **"이번 실행의 판정이 전부 끝났다"** 를 뜻한다(F-005, 커밋 `ed6ccab`). 위 측정치의 의미는 바뀌지 않는다 — 측정 당시에는 assert 가 없어 두 정의가 같은 시점을 가리켰다.

### 부수 확인

- **샌드박스 격리:** iframe에서 `parent.document` → `SecurityError`, `localStorage` → `SecurityError`, `origin` → `null`. `sandbox` 속성값 `allow-scripts` 단독.
- **부모 응답성:** 6초 블로킹 루프 중에도 부모 페이지 정상 동작. Worker 전환 불필요.
- **좀비 프로세스 없음:** 강제 종료 후 16초간 `top` 4회 샘플링 — 100%에 붙은 렌더러 프로세스 없음. `frame.remove()`가 실제로 루프를 종료시킨다.
- **워치독 방어:** `clearInterval`/`clearTimeout` 래핑으로 타이머 id 무차별 해제(300회) 후에도 ping 유지. 실측 확인.

### 통과했으나 한계가 확인된 항목

블로킹 실행 중 발생한 `console.log`는 부모에 도달하지 않는다. → **F-006**

## 트랜스파일러 실측 (2026-08-20)

**PRD §6.3 의 잠정 결정(Sucrase)을 확정 결정(@babel/standalone)으로 뒤집은 근거.**

측정 환경 — Chrome, localhost 부모 문서, CDN 은 esm.sh(트랜스파일러)·unpkg(React UMD). 각 1회 측정.

### 1. 로드 비용

**바이트는 압축 해제 기준이다.** cross-origin 리소스에 `Timing-Allow-Origin` 이 없어 `transferSize` 가 0 으로 나온다. F-007 과 같은 조건이며 같은 단위로 비교해야 한다.

| 후보 | 크기 | 파일 수 | 콜드 로드 | 변환 1회 (200회 평균) |
|---|---:|---:|---:|---:|
| Sucrase 3.35.0 | 251,703 B (246 KB) | 16 | 973 ms | **0.29 ms** (58 ms) |
| **@babel/standalone 7.26.4** | 2,972,188 B (2,903 KB) | 2 | **888 ms** | 0.76 ms (151 ms) |
| esbuild-wasm 0.24.2 | 96,137 B + wasm 11,907,565 B = 12,003,702 B (11,722 KB) | 3 + wasm | 1,689 ms | 10.03 ms (2,006 ms) |
| React 18.3.1 UMD (react + react-dom, production) | 142,586 B (139 KB) | 2 | 188 ms | — |

esbuild 의 wasm 초기화는 바이너리가 캐시된 뒤 61 ms 였다. 위 1,689 ms 는 wasm 내려받기 시간이다.

**크기가 11배 작은 Sucrase 가 더 느리다.** 모듈 그래프가 16파일이라 발견과 왕복이 직렬로 쌓인다. Babel 은 2파일이다. "작으니 빠를 것" 이라는 초판의 전제가 성립하지 않았다.

**§6.5 "T3/T4 첫 실행 1.5s" 대비** — 트랜스파일러와 React 는 병렬로 받을 수 있으므로 둘 중 큰 쪽이 기준이 된다.

| 후보 | T3 진입 추가 크기 | 병렬 가정 시간 | 판정 |
|---|---:|---:|---|
| Sucrase | 385 KB | 973 ms | 충족 |
| **@babel/standalone** | 3,042 KB | **888 ms** | **충족** |
| esbuild-wasm | 11,862 KB | 1,689 ms | **초과** |

### 2. 구문 에러 메시지

JSX 를 처음 쓰는 사람이 낼 법한 실수 넷으로 쟀다.

| 실수 | Sucrase | @babel/standalone | esbuild-wasm |
|---|---|---|---|
| 닫는 태그 누락 (`<h1>제목` 미닫음, 5행) | `Unexpected token, expected ";" (1:16)` | `Unterminated JSX contents. (5:10)` + 코드 프레임 | `Unexpected closing "div" tag does not match opening "h1" tag @5:6` |
| `class` 대신 `className` (2행) | **통과** | **통과** | **통과** |
| 중괄호 짝 안 맞음 (`{name` 미닫음, 3행) | `Unexpected token, expected ";" (1:16)` | `Unterminated regular expression. (3:19)` + 코드 프레임 | `Unterminated regular expression @3:22` |
| 여러 요소를 감싸지 않고 반환 (4행) | `Unexpected token, expected ";" (1:16)` | `Adjacent JSX elements must be wrapped in an enclosing tag. Did you want a JSX fragment <>...</>? (4:4)` + 코드 프레임 | `Unterminated regular expression @4:17` |

**Sucrase 는 세 오류 모두 같은 메시지에 같은 위치를 낸다.** `1:16` 은 `const App = () => {` 의 화살표 위치이며, 어떤 실수를 하든 이 값이 나온다. **학습자는 4행의 오타를 1행에서 찾게 된다.**

Babel 은 위치가 정확하고 코드 프레임이 붙으며, 마지막 사례에서는 고칠 방법까지 제시한다. esbuild 는 위치는 정확하지만 두 사례에서 `Unterminated regular expression` 이라는 실제 원인과 다른 이름을 붙인다.

### 3. 줄 번호 보존 — 결정 요인

입력 11행 중 **10행**에 마커를 두고 변환 후 출력 위치를 봤다.

| 후보 | 마커 출력 행 | 출력 총 행 | 판정 |
|---|---:|---:|---|
| Sucrase | 10 | 11 | 보존 |
| @babel/standalone (기본) | 8 | 9 | 밀림 |
| **@babel/standalone + `retainLines: true`** | **10** | **11** | **보존** |
| esbuild-wasm | 4 | 6 | 깨짐 |

**`retainLines: true` 로 소스맵 없이 보존된다.** Babel 을 배제할 유일한 기술적 이유였던 항목이 사라진다. `runner.js` 의 `lineno - offsetOf(head)` 산술을 그대로 쓸 수 있다.

esbuild 는 공백을 접어 11행을 6행으로 줄인다. 채택하려면 소스맵이 필수이고, 위 산술을 소스맵 조회로 교체해야 한다.

### 4. `class` vs `className` — 셋 다 잡지 못한다

세 후보 모두 **통과**시킨다. `class` 는 JSX 구문으로 유효한 속성명이라 파서가 걸러 낼 이유가 없다. 오류 없이 변환되고, 화면에는 스타일만 조용히 빠진 채 나온다.

**검사로 막을 수 없으므로 레슨 설계가 막아야 한다.** F-010 과 같은 성질이다 — 결과만 보는 검사는 이 실수를 구분하지 못한다. **T3-1(JSX 문법과 HTML 의 차이)이 정확히 그 자리다.** 그 레슨의 지문이 이것을 명시적으로 세워야 하며, PRD §4 T3 에 설계 조건으로 남겼다.

### 미측정

| 항목 | 사유 |
|---|---|
| 압축 전송 바이트 | cross-origin 에 `Timing-Allow-Origin` 이 없어 `transferSize` 가 0. 위 수치는 전부 압축 해제 기준 |
| 다른 네트워크에서의 콜드 로드 | 측정자의 연결에서 각 1회. 회선이 느리면 Babel 의 2.9 MB 가 불리해지는 지점이 있다 |

| `retainLines` 의 여러 줄 JSX 정렬 | 마커 1개 기준으로만 확인했다. M2 에서 확인한다 |

## T3 착수 전 실측 (2026-08-20)

레슨을 쓰기 전에 두 가지를 확인했다. **하나는 설계대로였고 하나는 전제가 틀렸다.**

### 1. `key` 우회 — 재현됨

`key` 의 실질적 피해는 상태가 있어야 드러나는데 상태는 T4 다. **비제어 `<input>`** 으로 우회할 수 있는지 쟀다. 목록을 `root.render()` 로 두 번 그리며 순서를 뒤집고, 첫 입력창의 DOM 값을 미리 채워 두었다.

| 표기 | 순서 바꾼 뒤 이름 | 입력값 | 0번 input 이 같은 DOM 노드인가 |
|---|---|---|---|
| `key` 없음 | 양말,모자,셔츠 | **셔츠에적음**,-,- | true |
| `key={index}` | 양말,모자,셔츠 | **셔츠에적음**,-,- | true |
| `key={item.id}` | 양말,모자,셔츠 | -,-,**셔츠에적음** | false |

**입력값이 자리에 남아 엉뚱한 항목 옆에 붙는다.** `key` 를 주면 셔츠를 따라 3번째로 이동한다. 상태 없이 재현되므로 `t3-09` 를 설계대로 쓸 수 있다.

### 2. `class` vs `className` — 전제가 틀렸다

"`class` 로 쓰면 스타일이 조용히 빠진다" 는 전제로 `t3-01` 을 설계했다. **틀렸다.**

| 빌드 | 표기 | DOM 의 class 속성 | 적용된 스타일 | 경고 |
|---|---|---|---|---|
| production | `className` | `"card"` | 테두리 3px · padding 9px | 없음 |
| production | `class` | `"card"` | 테두리 3px · padding 9px | **없음** |
| development | `class` | `"card"` | 테두리 3px · padding 9px | `Invalid DOM property \`class\`. Did you mean \`className\`?` |

**React 18 은 모르는 속성을 그대로 요소에 넘긴다.** `class` 로 써도 결과가 완전히 같다. production 빌드에서는 **잘못을 알 방법이 아예 없다** — 화면도 같고 콘솔도 조용하다. 학습자는 틀린 습관을 아무 신호 없이 굳히게 된다.

**그래서 개발 빌드로 바꿨다**(PRD §6.1). 개발 빌드는 `class`·`for`·`key` 누락을 콘솔로 알려 준다. React 경고는 `console.error` 로 나오므로 콘솔 패널에 오류 색으로 표시된다.

**§6.3 이 알던 것보다 한 겹 더 나쁘다.** §6.3 은 트랜스파일러 셋이 `class` 를 잡지 못한다는 것까지 알았다. **React 런타임도 잡지 못한다는 것은 이번 실측에서 나왔다.** 변환 단계와 실행 단계 어디에도 신호가 없다.

**T4 에서 되돌릴 수 없게 된다.** `key` 누락, 훅 규칙 위반, 조건부 훅 호출은 전부 개발 빌드 전용 경고다. production 으로 두면 T4 에서 같은 결정을 다시 해야 하고, 그때는 이미 T3 레슨 16개가 production 전제로 쓰여 있다. **지금 바꾸는 것이 가장 싸다.**

| | production | development |
|---|---:|---:|
| 크기(압축 해제) | 142,586 B | 1,190,136 B |
| 줄 수 | 300 | 33,269 |
| 콜드 로드 | 220 ms | 338 ms |

**+1,023 KB · +118 ms 다.** Babel(888 ms)과 병렬로 받으므로 **체감 시간은 늘지 않는다.** 줄 번호 보정도 33,529줄을 주입한 뒤 정확했다(사용자 코드 5행 오류 → `@33534 - 33529 = 5`).

### T3-1~3 관찰 실측

지문이 주장하는 것을 실제 프레임에서 확인했다.

| 레슨 | 지문의 주장 | 실측 |
|---|---|---|
| `t3-01` ② | `class` 로 바꾸면 화면은 같고 콘솔에 경고 | `Warning: Invalid DOM property \`class\`…` |

## T4 착수 전 실측 (2026-08-21)

레슨을 쓰기 전에 위험 세 건을 쟀다. **둘은 설계대로였고 하나는 예상보다 나빴다.**

### 1. 상태 스냅샷 — 재현됨

```
렌더 · 이번 렌더의 count = 1
   setCount 직후 count = 1        ← 옛 값
렌더 · 이번 렌더의 count = 2
   화면 = 2개
```

`setCount(count + 1)` 을 **같은 이벤트에서 두 번** 부른 경우:

```
렌더 · 이번 렌더의 count = 1
렌더 · 이번 렌더의 count = 2      ← 1 만 올랐다
   두 번 부른 뒤 화면 = 2개
```

`setCount(count + 2)` 로 한 번에 계산하면 `1 → 3` 으로 2 가 오른다. **`t4-03` 을 설계대로 쓸 수 있다.**

### 2. 훅 규칙 — 재현되나 **한 경우는 조용히 지나간다**

**되돌아올 때도 조용하다(추가 실측).** 훅 1개 → 0개 → 1개 왕복을 시켰는데 양방향 모두 오류가 없었다. 화면도 정상 전환된다(`가` → `감춤` → `가`).

| 경우 | 결과 |
|---|---|
| 훅이 **늘어남** (조건이 참이 되어 `useState` 추가 호출) | `Uncaught Error: Rendered more hooks than during the previous render.` + `Warning: React has detected a change in the order of Hooks…` · **화면이 빈다** |
| 훅이 **줄어듦** (조건이 거짓이 되어 호출이 빠짐) | `Uncaught Error: Rendered fewer hooks than expected. This may be caused by an accidental early return statement.` · **화면이 빈다** |
| **이른 `return` 뒤에 훅** (훅 1개 → 0개) | **오류 없음. 화면 정상 전환.** |

**세 번째가 중요하다.** 훅을 하나도 부르지 않게 되는 렌더는 React 가 잡지 못한다. `t4-05` 의 지문은 "React 가 알려 준다" 가 아니라 **"어떤 경우는 오류로 막히고 어떤 경우는 조용히 지나간다. 그래서 규칙을 지키는 것이지 오류가 알려 주기를 기다리는 것이 아니다"** 로 써야 한다. F-010 계열의 또 다른 사례다 — 도구가 전부 잡아 주지 않는다.

### 3. cleanup — 재현됨

정리하지 않은 `setInterval` 은 컴포넌트를 언마운트한 뒤에도 계속 돈다.

```
정리 안 함 :  tick 1, tick 2, === 없앰 ===, tick 3, tick 4   ← 계속 돈다
정리 함     :  tick 1, tick 2, === 없앰 ===, 정리했습니다      ← 멈춘다
```

**`t4-14` 를 설계대로 쓸 수 있다.**

## 파생 상태와 useEffect 실측 (2026-08-21)

`t4-10`·`t4-12` 지문의 근거다.

### 파생 상태가 어긋나는 순간

검색어와 개수를 각각 상태로 두고, 지우기 버튼이 검색어만 고치게 두었다.

```
검색 뒤   · 입력창 = "리액트"  개수 = 코스 1개
지우기 뒤 · 입력창 = ""       개수 = 코스 1개    ← 어긋남
```

**오류도 경고도 없다.** 보는 사람만 이상하다고 느낀다.

### `useEffect` 로 파생하면 어긋난 프레임이 실제로 그려진다

| 방식 | 한 글자 칠 때의 렌더 로그 |
|---|---|
| `useEffect` + 상태 | `검색어="리액트" / 결과=3개` → `검색어="리액트" / 결과=1개` |
| 그냥 계산 | `검색어="리액트" / 결과=1개` |

**첫 줄이 어긋난 화면이다.** 검색어는 이미 바뀌었는데 결과가 옛것인 렌더가 한 번 실제로 지나간다. 짧아서 눈에 잘 안 띌 뿐이다. 계산으로 바꾸면 렌더가 한 번이고 그 줄이 없다.

### 의존성 배열을 빼면 — **레슨에 넣지 않기로 했다**

`useEffect(() => setN(n + 1));` 처럼 배열을 생략하면 `Warning: Maximum update depth exceeded.` 가 뜨고 React 가 멈춘다. **워치독 강제 종료는 없다.** 다만 실측에서 **경고가 1,832줄** 쏟아졌다. 학습자의 콘솔 패널이 그것으로 가득 찬다(F-004 — 콘솔 로그 상한 없음). `tweak` 으로 쓰면 관찰보다 잡음이 커서 넣지 않았다.

### 자식이 각자 상태를 두면

```
입력창 = "리액트"  |  목록의 개수줄 = 코스 3개
```

`t4-11` 의 관찰거리다. 검색창은 잘 움직이는데 목록이 모른다.

## 공통 원인 R-1 — 블로킹 중 크로스프로세스 전달 미플러시

F-003 과 F-006 은 별개 버그가 아니다. **같은 현상이 두 곳에서 드러난 것**이다. 원인은 여기 한 곳에만 적고, 두 항목은 이 절을 참조한다.

**현상** — 자식(sandbox iframe)이 `postMessage` 를 호출해도, 자식 메인 스레드가 이벤트 루프를 양보하기 전까지 부모에 전달되지 않는다. **호출이 늦는 것이 아니라 전달이 늦는다.**

**계측** — 프로덕션과 동일 조건(`sandbox="allow-scripts"`, srcdoc, script 태그 분리)의 프로브 프레임에서 자식의 호출 시각과 부모의 수신 시각을 분리 측정.

2초 블로킹:

```
A_prelude_sync   child=5ms      parent=2008ms   ← 호출 5ms, 도착 2008ms
B_microtask      child=5ms      parent=2008ms
D_after_block    child=2005ms   parent=2008ms
E_done_slot      child=2005ms   parent=2008ms
C_timeout0       child=2006ms   parent=2008ms
```

블로킹 없는 대조군은 전원 `child≈8ms / parent=18ms`.

**해석** — 프렐류드의 첫 ping 은 script 태그 파싱 시점에 **동기 실행된다**(자식 기준 5ms). 마이크로태스크도 타이머도 경유하지 않는다. 그럼에도 5건 전부 블로킹이 끝난 뒤 `parent=2008ms` 에 **일괄 도착**했다.

**따라야 하는 결론** — 자식이 보내는 어떤 신호도 블로킹 구간을 건너오지 못한다. 따라서 **자식 신호만으로는 "실행 중 멈춤"과 "프레임 시작 실패"를 구분할 수 없다**(둘 다 도착 0건). 부모가 직접 받는 신호(iframe `load`)를 함께 봐야 갈린다.

| 프레임 상태 | `load` | ping | 3초 시점 판정 |
|---|---|---|---|
| 정상 코드 | 19ms | 21ms | — |
| 3초 블로킹 | 3006ms (임계값 이후) | 3006ms | `!load && !ping` → 실행 중 멈춤 |
| 스크립트 실행 불가 프레임 | 10ms | 0건 | `load && !ping` → 시작 실패 |

러너가 실제로 만드는 iframe 에서도 재측정했다. 정상 코드 `load` 210ms, 4초 블로킹 `load` 4154ms — 초기 about:blank 로드가 `load` 를 앞당겨 때리는 일은 없다(srcdoc 를 붙이기 전에 넣는 순서 유지 조건).

## 미해결 항목

### F-001 프레임 단위 스로틀 오탐 — **틀렸음 (2026-08-21 정정)**

- **처리 상태** — **항목 자체가 틀렸다.** 프레임 단위 스로틀은 없다. 원인은 **페이지(탭) 가시성**이고, 그것은 이미 `document.hidden` 가드가 다루는 범위다. 아래 정정 참조.
- **원래 증상 기술** — 정상 동작 중인 프레임을 워치독이 죽일 수 있다. 자식의 ping 타이머가 지연되면 부모가 "멈춤"으로 오판한다.
- **원래 원인 판단(틀림)** — 실행 프레임이 0×0 + opaque origin 이라 **크롬이 프레임 단위로 타이머에 개입하고, 그래서 탭이 앞에 있어도 발생할 수 있다**고 적었다. 근거가 없는 추정이었고 그대로 M0 부터 기록에 남았다.
- **정정 근거 (실측)** — 같은 앱에서 프레임 크기만 다르게 두고 ping 간격을 쟀다.

| 조합 | 프레임 크기 | ping 간격 (설정 500ms) |
|---|---|---|
| 미리보기 꺼짐 · 탭 뒤 | 0×0 | 중앙값 **1000ms** (n=45 · 922~1009) |
| 미리보기 켜짐 · 탭 뒤 | 833×234 | 중앙값 **1000ms** (n=14 · 996~1006) |

**두 값이 같다.** 프레임 크기도, 화면에 붙었는지도 간격을 바꾸지 못했다. 조이는 것은 탭 가시성 하나다.

- **이 오판이 만든 비용** — "미리보기 프레임이 실제 크기로 화면에 붙는 T2 때 재검증한다 / 그러면 해소될 것이다" 라는 계획을 세웠다. **해소될 일이 아니었다.** 붙는 것과 무관한 문제였기 때문이다. 그 계획 때문에 항목이 T2 → T5 까지 미해결로 끌려다녔고, T5 내내 측정을 방해했으며 `t5-13` 에서는 지문 작성 방침까지 바꿔야 했다. **원인을 재지 않고 추정으로 적은 항목은 그 추정에 맞춘 계획을 낳는다.**
- **처리** — **코드는 이미 옳았다.** `runner.js` 의 `check()` 는 처음부터 `if (document.hidden) return;` 으로 막고 있었다. 틀린 것은 그 옆에 달린 주석과 이 F 항목이었다 — "부모의 `document.hidden` 가드는 탭 단위만 커버한다. 프레임 단위 스로틀은 막지 못한다" 는 문장이 그것이다. 막지 못하는 대상이 애초에 존재하지 않았다. 주석을 실측에 맞게 고치고 항목을 닫는다.

### F-002 ping 실측 간격이 설정값과 다름 — **처리 완료 (2026-08-21)**

- **처리 상태** — **처리 완료.** 원인이 확정됐고(탭 가시성), 오탐 경로를 막았다. 임계값은 3초 그대로 둔다.
- **증상** — 프렐류드는 500ms 로 ping 을 보내는데 도착 간격이 다르다.
- **수치 정정 — 830ms 가 아니라 1000ms 다.** 이전 값은 테스트 A~E 를 진행하며 눈에 띈 표본을 손으로 읽은 것이라 **가시 구간과 비가시 구간이 섞여 있었다.** 자동 계측으로 조합을 갈라 재니 탭이 뒤에 있을 때 **중앙값 1000ms · 범위 996~1009ms** 로 매우 안정적이었다. 브라우저가 숨겨진 페이지의 타이머를 1초로 고정한다.
- **판단 — 임계값 상향은 하지 않는다.** 최악값 1000ms 에 임계값 3000ms 면 ping **3회분 여유**이고 흔들림은 ±10ms 다. 올릴 근거가 없다. 그리고 숫자로는 막을 수 없는 부류가 따로 있다 — 크롬은 오래 숨겨진 페이지의 타이머를 **분당 1회**까지 조일 수 있고, 그 경우 3초든 5초든 똑같이 오탐이다.
- **처리** — `document.hidden` 인 동안 워치독 검사를 건너뛰는 가드는 **이미 들어 있었다**(`runner.js` `check()`). 새로 넣을 것이 없었다. 학습자가 보고 있지 않은 화면에 "멈췄습니다" 를 띄울 이유가 없고, 돌아오는 순간은 `handleVisibility` 가 `lastPingAt` 을 재설정한다. 스로틀이 얼마나 심하든 이 경로의 오탐이 사라진다. **나는 이 가드를 못 보고 "추가하자" 고 제안했다.** 코드를 다시 읽고 정정했다.
- **`ASYNC_TIMEOUT_MS` 를 올린 것과는 다른 판단이다.** 그쪽은 레슨 내용이 순차 요청으로 바뀌어 **전제가 깨졌고 실제 통과 실패가 관측됐다.** 이쪽은 전제가 그대로이고 오탐이 한 번도 관측되지 않았다. 같은 "숫자를 올리자" 로 보이지만 근거의 유무가 반대다.

- **증상** — 부모 콘솔 패널에 쌓이는 `<li>` 노드에 상한이 없다. 대량 출력 시 DOM 노드가 무제한 증가한다.
- **재현 조건** — `while (true) console.log(1)`. 크롬은 견뎠으나 이는 우연이며 보장된 동작이 아니다.
- **판단** — 상한 **1000줄**을 두고 초과분은 앞에서 버린다(버린 사실은 표시).
- **처리 시점** — **M1.**

### F-005 `done`이 비동기 완료를 판정하지 못함

- **처리 상태** — **처리 완료** (커밋 `ed6ccab`). `value` assert 가 반환값이 thenable 이면 `await` 한 뒤 비교하고, 모든 assert 가 끝난 다음 `done` 이 발신된다. `done` 의 정의를 **"이번 실행의 판정이 전부 끝났다"** 로 갱신했다.
- **증상** — `done` 은 동기 실행이 끝난 시점에만 발신됐다. 함수가 Promise 를 반환하면 아직 실행 중인데도 완료로 표시됐고, 검사 시점을 잡을 신호가 없었다.
- **재현 조건** — 해소됨. 이전에는 `setTimeout(() => console.log('끝'), 500)` 에서 `done` 이 즉시 왔다.
- **판단** — 러너를 고칠 필요가 없었다. 필요한 것은 assert 계약의 확장 하나였고, 부모가 이미 `done` 을 마감 신호로 쓰고 있었으므로 정의를 넓히는 쪽이 오히려 정확해졌다.
- **남는 제약 (처리 결과로 기록)**
  - **워치독은 영영 resolve 되지 않는 Promise 를 잡지 못한다.** 프레임의 이벤트 루프가 살아 있어 ping 이 계속 흐르기 때문이다. 대신 **assert 레벨 2초 타임아웃**이 끊는다. 실측: `new Promise(() => {})` 반환 시 3건 모두 `Error: 결과가 2초 안에 완료되지 않았습니다` 로 보고되고 화면은 멈추지 않았다. **학습자에게 보이는 증상은 없다.**
  - **reject 케이스는 다루지 않는다.** `expected` 가 JSON 값이라 검사 대상은 resolve 된 값뿐이다. 거부된 Promise 는 `error` 상태로만 보고된다.
  - **assert 타임아웃은 백그라운드 탭 스로틀의 영향을 받는다.** 지연 45ms 가 3002ms 로 부풀어 측정된 적이 있다.
    → 그래서 **레슨의 비동기 지연은 1초 미만으로 제한한다**를 작성 규칙으로 두었다. 현재 `t1-17` 이 쓰는 값은 0·100·200ms 다.
- **처리 시점** — 처리 완료. T1-8 에 필요한 범위는 확보됐다.

### F-006 블로킹 중 `console.log` 미도달

- **처리 상태** — **처리 완료(완화)** (커밋 `20df4bd`). 사용자 브라우저 실측 확인: 강제 종료 안내에 "이 시점까지 도착한 로그만 표시됩니다"가 표시된다.
  **단, 원인 R-1 자체는 해결되지 않았다.** 블로킹 직전 로그는 여전히 도착하지 않으며, 학습자에게 그 사실을 알리는 것까지가 이 항목의 처리 범위다. 완화만 된 상태다.
- **증상** — 무한 루프에 빠지면 **그 이전에 찍은 로그도** 부모에 도달하지 않는다. 학습자는 강제 종료 안내만 보고 어디서 멈췄는지 알 수 없다.
- **재현 조건** — `console.log('시작')` 직후 `while (true) {}`. 6초 블로킹에서 도착 0건. 1초 블로킹 대조군에서는 루프 종료 후 일괄 도착.
  **트리거는 레슨 주제와 무관하다.** 무한 루프를 가르치는 레슨이 있느냐와 별개로, T1-5(조건·반복)에서 학습자가 증감 방향을 실수하면 바로 밟는다.
- **판단** — 유실이 아니라 **발신 지연**이다. **원인은 → 공통 원인 R-1.** 워치독이 프레임을 제거하면서 대기 중이던 큐가 함께 소멸한다. `allow-same-origin` 없이 쓸 수 있는 채널이 `postMessage` 뿐이라 근본 해결책이 없다. **해결이 아니라 완화 항목으로 둔다.**
- **처리 시점** — **M1.** 강제 종료 안내에 "이 시점까지 도착한 로그만 표시됩니다" 한 줄을 추가한다. 학습자가 도구를 의심하지 않게 하는 것이 목적이다.

### F-008 비동기 에디터 마운트가 엉뚱한 단계에 붙는다

### F-009 `srcdoc` 프레임에서 경로·쿼리 라우팅 불가

- **처리 상태** — **제약으로 확정.** 우회 방법 없음. 해시 라우팅으로 대체 가능하므로 결함이 아니라 설계 입력이다. PRD §4 T6에 기록했다.
- **측정** — 2026-08-20, Chrome. 부모 문서 `http://localhost:878`, 자식은 `srcdoc` iframe. **샌드박스 프레임과 비샌드박스 프레임을 대조군으로 함께 측정했다.**

  | 호출 | `sandbox="allow-scripts"` | 샌드박스 없음 |
  |---|---|---|
  | `pushState({}, '', '#a')` | SecurityError | SecurityError |
  | `pushState({}, '', '/path')` | SecurityError | SecurityError |
  | `replaceState({}, '', '#c')` | SecurityError | SecurityError |
  | `pushState({}, '', location.href + '#b')` | OK → `#b` | OK → `#b` |
  | `location.hash = 'd'` | OK → `#d` | OK → `#d` |
  | `hashchange` / `popstate` | 2회 / 1회 | 2회 / 1회 |

- **판단** — 원인은 **샌드박스가 아니라 `about:srcdoc`이다.** 비샌드박스 프레임은 origin이 `http://localhost:878`인데도 동일하게 실패했다. `about:srcdoc` 문서는 base URL을 부모에서 물려받으므로 상대 URL이 부모 주소로 해석되고, 문서 URL과 어긋나 거부된다.

  브라우저 메시지: `A history state object with URL 'http://localhost:878/#a' cannot be created in a document with origin 'null' and URL 'about:srcdoc'.`

  **`allow-same-origin`을 붙여도 해결되지 않는다.** 라우팅은 샌드박스 경계와 맞바꿀 대상이 아니다.

- **`<base href="about:srcdoc">` 실측** — 상대 `pushState`·`replaceState`는 통과하게 되지만, scaffold의 상대 경로 자산이 깨진다(`pic.png` → 해석 불가). 쿼리스트링(`?q=1`)은 base를 바꿔도 여전히 실패한다. **채택하지 않는다** — 해시 라우팅이 base 변경 없이 동작하므로 대가를 치를 이유가 없다.

- **미측정** — react-router 자체는 재지 않았다. `createHashHistory`가 `pushState`에 상대 문자열 `'#/foo'`를 넘기는 구조라 위 1행과 같은 실패에 걸릴 것으로 본다. 그 라이브러리는 예외를 잡아 `location.assign(url)`로 폴백하는데, 그러면 프레임이 부모 주소로 실제 이동해 실행 중인 코드가 사라진다. **추정이며 확인하지 않았다.** T6 착수 전에 측정한다.

- **앞으로 주의할 것** — `srcdoc` 프레임 안에서 **문서 URL을 건드리는 API는 전부 같은 함정**이 있다. 원인이 origin이 아니라 base URL이므로, 샌드박스 속성을 아무리 조정해도 달라지지 않는다.

### F-010 결과만 보는 검사는 구현 방식을 강제하지 못한다

- **처리 상태** — **고치지 않는다.** 검사 설계의 구조적 한계이며 버그가 아니다.
- **증상** — `t2-06`(목록을 한 번에 듣기)의 `write` 단계는 이벤트 위임을 요구하지만, 학습자가 담기 버튼마다 개별로 `addEventListener` 를 붙여도 **5개 assert 가 전부 통과한다.** 위임을 쓰지 않은 답과 쓴 답이 검사로 갈리지 않는다.
- **왜 막을 수 없는가** — 개별 바인딩이 실제로 실패하려면 요소가 **나중에 추가되어야** 한다. 요소를 코드로 만드는 것은 `t2-09`(데이터로 목록 그리기)부터다. `t2-06` 시점에는 화면의 버튼이 처음부터 셋이고 늘지 않으므로, 두 구현이 만들어 내는 DOM 상태가 완전히 같다.
- **판단** — **같은 성질이 앞에도 있었다.** `value` assert 는 `t1-02`에서 `if`/`else` 와 삼항 연산자를 구분하지 못하고, `t1-09`에서 클로저를 썼는지 전역 변수를 썼는지 구분하지 못한다. 반환값이든 DOM 상태든 **결과만 보는 검사는 구현 방식을 강제하지 못한다.** 이것은 `dom` assert 를 추가하면서 생긴 문제가 아니라 검사 방식 자체의 성질이다.

  **억지로 막으려 하면 문제가 이상해진다.** 소스 문자열을 검사하거나 `addEventListener` 호출 횟수를 세는 방향은 학습자가 정답을 맞히고도 실패하는 경로를 만든다. 구현 방식을 묻고 싶으면 검사가 아니라 **문제 형태로 막아야 한다.**
- **처리** — `t2-06` 에서는 지문으로만 요구한다. **`t2-11`(검색으로 걸러 그리기)에서 실제로 강제된다.**

  그 레슨의 `write` assert 는 검색어를 넣었다 지우며 목록을 여러 번 다시 그린 **뒤에** 담기 버튼을 누른다. 개별 바인딩은 첫 재렌더에서 끊기므로 이 마지막 assert 를 통과하지 못한다. 카드마다 `addEventListener` 를 붙인 오답으로 실측했다.

  ```
  통과 — 처음에는 코스가 셋 다 보입니다
  통과 — '리액트' 를 치면 한 장만 남습니다
  통과 — 맞는 것이 없으면 안내가 보입니다
  통과 — 지우면 전체가 돌아옵니다
  실패 — 여러 번 다시 그린 뒤에도 담기가 동작합니다
          기대 ["담은 코스: 리액트 시작하기"] | 실제 ["담은 코스: 없음"]
  ```

  **검사를 고쳐서가 아니라 문제를 바꿔서 강제됐다.** 요소가 다시 만들어지는 상황을 scaffold 가 만들어 내므로, 위임을 쓰지 않은 답과 쓴 답의 DOM 상태가 비로소 갈린다. `t2-15`(종합)에서 같은 조건을 다시 쓸 수 있는지는 그 레슨을 쓸 때 검토한다.
- **앞으로 주의할 것** — 레슨을 쓸 때 **"검사가 가려 주겠지"로 요구사항을 미루지 마라.** 검사로 갈리지 않는 요구는 지문에 쓰더라도 갈리지 않는다. 구현 방식을 배우게 하려면 그 방식이 아니면 실패하는 상황을 scaffold 로 만들어야 한다.

### F-011 초점 관련 동작은 개발 환경에서 판정할 수 없다

- **처리 상태** — **환경 제약으로 확정. 실제 브라우저에서는 정상 동작한다.** 레슨 수정 없음.
- **사용자 브라우저 실측 (2026-08-20)** — `포커스 옮기기` → `2 실행` 에서 '짧은 코스만' 을 누르니 콘솔에 **`지금 초점: DIV result`** 가 찍혔다. **샌드박스 `srcdoc` 프레임 안에서 `focus()` 는 정상 동작한다.**
- **정정 내용** — 앞선 보고에서 원인 후보로 "opaque origin 하위 프레임의 제약" 을 올렸다. **그것이 아니었다.** 원인은 개발 환경의 탭에 시스템 초점이 없다는 것 하나였다.

  | 대상 | 개발 환경(`hasFocus() === false`) | 실제 브라우저 |
  |---|---|---|
  | 부모 문서의 `<input>` | `activeElement` 이동함 | 정상 |
  | 프레임 안 `<div tabindex="-1">` | **BODY (이동 안 함)** | **정상 (`DIV result`)** |
  | `:focus` 선택자 | 부모·프레임 모두 매칭 0 | 문서에 초점이 있어야 매칭 |

  속성 선택자(`[aria-expanded="true"]` · `[tabindex="-1"]`)는 양쪽 모두 정상이다.

- **`:focus` 를 assert 에 쓰지 않는 판단은 유지한다.** 이 선택자는 문서가 시스템 초점을 가져야 매칭된다. 학습자가 다른 탭을 보고 있거나 창이 배경에 있을 때 **정답이 실패하는 경로**가 된다. `t2-14` 의 assert 는 `tabindex` 속성과 그려진 결과만 확인하며, 초점이 실제로 옮겨졌는지는 검사하지 않는다. F-010 과 같은 성질의 미강제 항목이다.

- **앞으로 주의할 것** — **초점·선택 영역·클립보드·`:focus` / `:focus-visible` / `:hover` 처럼 시스템 상태에 얹힌 것은 개발 환경에서 "동작하지 않는다" 고 판정하면 안 된다.** 개발 환경의 탭은 `document.hidden === true` · `document.hasFocus() === false` 로 고정돼 있다. 이 부류에서 관측이 비는 경우, 결론은 "동작하지 않는다" 가 아니라 **"이 환경에서는 판정할 수 없다"** 이고, 사용자 브라우저 확인을 요청해야 한다. 워치독 강제 종료(F-003 계열)가 같은 이유로 개발 환경에서 판정되지 않는 것과 같은 부류다.

### T5 착수 전 실측 — 실행 프레임의 `fetch` (2026-08-21)

`t5-06`~`t5-13` 의 설계 근거다. **나중에 진짜 요청으로 바꾸고 싶어질 때 프레임 권한부터 의심하지 않도록** 남긴다.

**프레임 정보** — `sandbox="allow-scripts"` · `location.origin` = `null` · `document.baseURI` = 부모 문서 URL(상속)

| 대상 | 로컬 (`python -m http.server`) | GitHub Pages |
|---|---|---|
| `fetch('lessons/index.json')` | **FAIL** `TypeError: Failed to fetch` (2ms) | **OK** `status=200` (2ms) |
| 절대 URL 같은 호스트 | **FAIL** `Failed to fetch` (0ms) | **OK** `status=200` (224ms) |
| 없는 파일 | — | **OK** `status=404`, `content-type: text/html` |
| `XMLHttpRequest` 상대경로 | **FAIL** `onerror`, `status=0` | 미측정 |

| 대상 | 결과 |
|---|---|
| CORS `*` 공개 API (jsonplaceholder) | OK `status=200` (338ms) |
| CORS 헤더 없는 사이트 (example.com) | FAIL `Failed to fetch` (120ms) |
| `data:` URL | OK `status=200` (1ms) |
| `blob:` URL | OK `status=200` (4ms) |
| `new Response(...)` 직접 생성 | OK — `ok`·`status`·`statusText`·`headers.get()`·`json()` 전부 동작 |
| `window.fetch` 덮어쓰기 | OK |
| `Response.json()` 파싱 실패 | `SyntaxError: Failed to execute 'json' on 'Response': Unexpected token '<', "<!doctype "... is not valid JSON` |
| `AbortController` | OK — `DOMException: signal is aborted without reason` |

**막는 것은 샌드박스가 아니라 CORS 헤더다.**

```
GitHub Pages  →  access-control-allow-origin: *      → 통과
python http.server →  (헤더 없음)                    → 차단
```

프레임의 origin 이 `null`(opaque)이므로 **같은 호스트의 파일을 받는 것도 교차 출처 요청**이 된다. 서버가 `Access-Control-Allow-Origin` 을 보내야 통과한다. `allow-same-origin` 을 붙이면 해결되지만 **그것은 절대 하지 않는다**(CLAUDE.md 보안 항목. 부모 DOM·스토리지가 열린다).

**따라서 진짜 fetch 는 배포판에서만 동작하고 로컬에서는 전부 실패한다.** 전수 회귀를 로컬에서 돌리는 현재 체계로는 검증할 수 없다. 이것이 가짜 fetch 를 택한 이유다. 프레임 권한 문제가 아니다.

**나중에 진짜 요청으로 바꾸려면 필요한 것** — 프레임 권한이 아니라 **CORS 헤더를 보내는 로컬 서버** 하나다. 배포판 쪽은 이미 된다.

**T6 에서 같은 결정을 다시 하게 된다.** React 에서 데이터를 가져오는 트랙이고, 그때도 같은 갈림길에 선다. T5 와 같은 가짜 fetch 를 그대로 쓰는 것이 기본안이다.

**가짜 fetch 의 형태** — 레슨 `scaffold.html` 안 `<script>` 에서 `window.fetch` 를 갈아 끼운다. 앱 코드 변경 0줄, 레슨 스키마 변경 0건(`buildHead` 가 scaffold 를 사용자 코드보다 먼저 넣는다). 돌려주는 것은 흉내가 아니라 진짜 `Response` 객체이므로 학습자 코드는 진짜와 같다. 네트워크 실패는 실측한 문구 그대로 `TypeError('Failed to fetch')` 를 던져 맞춘다. **`t5-06` read 에서 이 무대 장치를 밝힌다.**

**같은 동작, 두 형태** — `t5-05` 의 run 두 단계는 출력이 완전히 같다.

```
.then 형태      맡긴 뒤 바로 이 줄 / 성공: 리액트 입문 / 실패: 코스를 찾지 못했습니다
async/await     맡긴 뒤 바로 이 줄 / 성공: 리액트 입문 / 실패: 코스를 찾지 못했습니다
```

**`async`/`await` 세 가지**

```
async 없이 await        Uncaught SyntaxError: await is only valid in async functions
                        and the top level bodies of modules   ← 실행 전에 걸린다
await 만 제거           성공: undefined 가 두 번 · 순서가 앞당겨짐 · Uncaught (in promise)
async 함수의 반환        typeof object · instanceof Promise = true  (return 이 없어도)
```

`await` 를 지우면 세 가지가 한꺼번에 달라진다. 값이 Promise 가 되고, 함수가 기다리지 않아 동기적으로 끝나 출력 순서가 바뀌고, `try` 가 감싸고 있어도 거부가 잡히지 않는다.

**가짜 `fetch`(`env`)** — `t5-06` 무대.

```
정상 주소            ok=true status=200 ct=application/json · 세 코스
res.json() await 제거  받은 개수: undefined → Uncaught (in promise) TypeError: list.map is not a function
fetch 앞 await 제거    Uncaught (in promise) TypeError: res.json is not a function
없는 주소 (/api/nope)  Uncaught (in promise) SyntaxError: Failed to execute 'json' on 'Response':
                      Unexpected token '<', "<!doctype "... is not valid JSON
네트워크 실패          catch 로 TypeError | Failed to fetch
```

없는 주소가 **`catch` 가 아니라 `res.json()` 의 파싱 실패로 나타난다.** `t5-07`(`res.ok`) 의 필요를 그대로 보여 주는 자리라 `t5-06` tweak ③ 에 넣었다.

### 실측 환경의 한계 — 배경 탭 타이머 (2026-08-21)

### F-001 · F-002 재검증 (2026-08-21)

**F-001 정정 — 프레임 단위 스로틀이 아니다.** 0×0 프레임과 833×234 프레임의 간격이 **같다.** 프레임 크기나 화면에 붙었는지 여부는 상관이 없었다. 조이는 것은 **페이지(탭) 가시성**이다. `.sandbox-host` 를 0×0 으로 둔 것은 원인이 아니므로 마운트 위치를 바꿀 이유가 없다.

**F-002 정정 — 830ms 가 아니라 1000ms 다.** 이전 값은 눈에 띈 표본을 손으로 읽은 것이라 가시/비가시 구간이 섞였던 것으로 본다. 탭이 뒤에 있으면 브라우저가 타이머를 1초로 고정한다. 흔들림은 ±10ms 로 매우 작다.

**탭 앞은 내 환경에서 잴 수 없다.** 이 브라우저 도구의 페이지는 `document.visibilityState` 가 언제나 `hidden` 이다. 탭을 앞으로 올리고 스크린샷으로 그리게 해도 바뀌지 않았다. **F-011 과 같은 종류의 환경 제약이다** — 초점·선택·클립보드·`:focus` 처럼, 가시성에 기대는 값은 내 환경에서 판정할 수 없다. 계측 코드를 그대로 두었으니 사용자 브라우저에서 재야 한다.

**임계값 상향(3초 → 5초)에 대한 판단: 하지 않는다.**

- 재 본 최악값이 1000ms 다. 임계값 3000ms 는 **ping 3회분 여유**이고 흔들림은 ±10ms 다. 올릴 근거가 이 측정에는 없다.
- `ASYNC_TIMEOUT_MS` 와 맥락이 다르다. 그쪽은 **레슨 내용이 순차 요청으로 바뀌어 전제가 깨진 것**이었고, 실제로 2000ms 를 넘기는 통과 실패가 관측됐다. 이쪽은 전제가 그대로이고 실패가 관측되지 않았다.
- 진짜 위험은 다른 곳에 있다. 크롬은 오래 숨겨진 페이지의 타이머를 **분당 1회까지** 조일 수 있다. 그 경우 ping 이 60초에 한 번 오므로 **3초든 5초든 똑같이 오탐이 난다.** 숫자를 키우는 것으로는 이 부류를 막지 못한다.

**대신 제안** — `document.hidden` 인 동안 워치독 검사를 건너뛴다. 학습자가 보고 있지 않은 화면에 "멈췄습니다" 를 띄울 이유가 없고, 돌아오는 순간은 이미 `handleVisibility` 가 `lastPingAt` 을 재설정한다. 스로틀이 얼마나 심하든 오탐이 사라진다. **승인 전에는 넣지 않았다** — 학습자에게 보이는 경고 경로가 바뀌는 변경이다.

**사용자가 탭 앞 두 조합을 재는 절차**

1. 앱을 연다. 브라우저 콘솔을 열어 둔다.
2. **T5 · 11 한꺼번에 보내기** → 2단계(실행) → **실행**. 미리보기가 꺼진 레슨이다.
3. 탭을 앞에 둔 채 15초 기다린다. `[ping 측정]` 줄이 8건마다 찍힌다. **탭 앞** 값을 읽는다.
4. **T5 · 10 네 가지 얼굴** → 2단계(실행) → **실행**. 미리보기가 켜진 레슨이다. 같은 방식으로 읽는다.
5. 값을 알려 주면 계측 코드를 걷어낸다.

### T6 착수 전 실측 — react-router (2026-08-21)

F-009 에서 미측정으로 남긴 항목이다. **결론: 쓸 수 없다. `hashchange` 로 직접 만든다.**

**history API** — 프레임은 `about:srcdoc` · origin `null` 이다.

```
replaceState(state, '')        OK                     ← URL 인자가 없으면 통과
replaceState(state, '', '#/x') SecurityError          ← 해시만 바꿔도 막힌다
pushState(state, '', '#/y')    SecurityError
pushState(state, '', '/z')     SecurityError
```

메시지가 이유를 그대로 말한다 — `A history state object with URL '...' cannot be created in a document with origin 'null' and URL 'about:srcdoc'.` 해시만 바꾸는 URL 도 부모 문서 URL 기준으로 해석돼 막힌다.

**`location.hash` 대입과 `hashchange` 는 동작한다.**

```
location.hash = '#/courses'  →  location.hash = '#/courses' · hashchange 1회
```

**react-router v6 (6.26.2) UMD** — 전역 의존을 모두 채워 로드했다(`React`·`ReactDOM`·`RemixRouter`·`ReactRouter`·`ReactRouterDOM` 전부 `object`, `HashRouter` 와 `Routes` 는 `function`). 그런데 `HashRouter` 를 렌더하면 터진다.

```
TypeError: Failed to construct 'URL': Invalid URL   (3회)
렌더 결과: 본문 "" · 링크 0개
```

예상했던 `pushState` 가 아니라 **그보다 앞에서** 죽는다. 라우터가 `about:srcdoc` 을 base 로 `new URL(...)` 을 만들려다 실패한다. `about:srcdoc` 은 유효한 base URL 이 아니다. 어느 쪽이든 결론은 같다.

**따라서 T6 의 라우팅은 `hashchange` 로 직접 만든다.** 이미 그렇게 정해 두었고 이 측정이 그것을 확인했다. 부수 효과로 얻는 것도 있다 — 라우터가 무엇을 하는 물건인지 학습자가 직접 만들어 보게 된다. 다만 **실무에서는 react-router 를 쓴다는 것을 지문에 밝혀야 한다.** 여기서 직접 만드는 이유가 "라이브러리가 없어서" 가 아니라 "이 실행 틀에서 동작하지 않아서" 라는 것까지.

### T6 착수 전 실측 3건 (2026-08-21)

`t6-07`~`t6-14` 의 전제다. **①은 재현되지 않았고 ③은 새는 것이 확인됐다.**

**① `<form>` 제출 — 재현 실패. `submit` 이벤트가 아예 발생하지 않는다.**

실행 프레임은 `sandbox="allow-scripts"` 뿐이라 `allow-forms` 가 없다. 폼에 `submit` 리스너를 달고 다섯 가지 방법으로 제출을 시도했다.

```
버튼 클릭 · preventDefault 있음   → submit 이벤트 0회
버튼 클릭 · preventDefault 없음   → submit 이벤트 0회
form.requestSubmit()             → submit 이벤트 0회
form.submit()                    → submit 이벤트 0회
form.dispatchEvent(new Event('submit'))  → 1회   ← 우리가 직접 쏜 것
```

브라우저의 폼 제출 알고리즘이 **샌드박스 검사에서 멈추고, 그 검사는 `submit` 이벤트를 쏘기 전에 있다.** 그래서 이벤트가 아예 발생하지 않는다. 프레임은 멀쩡히 살아 있고(`readyState = interactive`, `href = about:srcdoc`) 폼도 입력값도 그대로다. 조용히 아무 일도 일어나지 않는다.

**결과: `t6-08`(제출 가로채기 · `onSubmit` · `preventDefault`)이 이 실행 틀에서 성립하지 않는다.** React 의 `onSubmit` 도 같은 이벤트에 붙으므로 마찬가지다. "`preventDefault` 를 빠뜨리면 페이지가 새로고침된다" 는 이 트랙의 핵심 체험도 재현할 수 없다.

**② 경쟁 조건 — 재현 성공.**

```
도착 순서: 빠른 것(나중 보냄) → 느린 것(먼저 보냄)
늦게 보낸 것이 먼저 도착했는가: true
덮어쓰기 결과 · 화면에 남은 것: A(먼저 보낸 요청의 응답)
```

지연이 다른 두 요청을 먼저/나중 순서로 보내면 **먼저 보낸 느린 응답이 나중에 도착해 화면을 덮는다.** `t6-05` 가 필요로 하는 상황이 그대로 만들어진다. 배경 탭 클램프가 1초로 고정이라 지연 차이가 뭉개질까 걱정했으나, 400ms 대 40ms 처럼 차이를 크게 두면 갈린다.

**③ `location.hash` — 주소는 안 새고 이력은 샌다.**

이력이 비어 있는 새 탭에서 쟀다(크롬의 세션 이력 상한이 50이라 오래 쓴 탭에서는 증가가 가려진다).

```
시작            부모 history.length = 2
'#/a' 대입      len 2 · hashchange 1
'#/b' 대입      len 3 · hashchange 2
'#/c' 대입      len 4 · hashchange 3
history.back()  프레임 hash = #/b · hashchange 4

부모 href 변화: 없음
부모 history.length: 2 → 4 (+2)
```

- **주소는 안 샌다.** 부모 문서의 `href` 도 `hash` 도 바뀌지 않는다.
- **이력은 샌다.** 프레임의 해시 변경마다 부모 탭의 세션 이력에 항목이 하나씩 쌓인다.
- **브라우저 뒤로가기가 프레임의 라우트를 되돌린다.** 프레임 안에서 `history.back()` 을 부르면 프레임 해시가 이전 값으로 돌아간다. 부모 탭의 뒤로가기 버튼도 같은 이력을 공유한다.
- **`location.replace('#/z')` 는 쓸 수 없다.** 그 호출 뒤로 프레임에서 아무 신호도 오지 않았다. 프레임 문서가 날아간 것으로 본다. 이력을 늘리지 않고 해시를 바꾸는 우회로 쓸 수 없다.

**결과: 라우터 레슨에서 링크를 N번 누르면 앱 탭의 뒤로가기 이력에 N개가 쌓인다.** 학습자가 브라우저 뒤로가기를 누르면 앱에서 나가는 대신 프레임의 이전 라우트로 돌아간다. 앱 쪽에서 막을 방법이 없다 — 프레임의 이력을 부모가 조작할 수 없다.

### T6 묶음 A 실측 (2026-08-21)

`t6-01`·`t6-02`·`t6-03` 의 근거다.

**비동기 React 레슨을 검사하는 방법** — 진입 함수가 없고 `dom` assert 는 `settle` 두 번 뒤에 읽으므로 요청이 끝나기 전 화면을 본다. 그래서 검사용 함수를 starter 에 **보이게** 두고 `value` assert 의 진입으로 쓴다.

```js
function show(url) {
  root.render(<CourseList key={url} url={url} />);
  return waitFor((t) => t.includes('불러오는 중'))      // 새 마운트를 확인하고
    .then(() => waitFor((t) => t && !t.includes('불러오는 중')));  // 끝나기를 기다린다
}
```

두 단계로 기다리는 이유가 있다. 한 번에 "로딩이 아닌 상태" 만 기다리면 **앞 검사가 남긴 화면**을 그대로 읽는다. 먼저 로딩이 나타나는 것을 확인해야 새 마운트가 시작된 것이 보장된다. `key={url}` 을 주는 것도 같은 이유다 — 같은 위치에 같은 컴포넌트를 다시 그리면 상태가 유지돼 효과가 다시 돌지 않는다(t3-09 의 key).

이 구성으로 **한 단계에서 네 갈래를 모두 검사한다.** 검사기가 `value` 를 순서대로 기다리므로 마지막에 성공 화면을 남겨 두고 `dom` assert 를 붙일 수 있다(실측 확인).

**처음 설계는 검사가 빈 칸을 건드리지 못했다.** `t6-02` fill 의 빈 칸은 "빈 목록 갈래" 인데 검사가 `/api/courses`(3개)만 봐서 **starter 가 그대로 통과했다.**

```
t6-02[5] starter 가 그대로 통과함
```

전수 회귀가 이것을 잡았다. 검사 하나가 주소 하나만 보면 갈래가 넷인 레슨을 검사할 수 없다. `show(url)` 로 바꾸고 네 주소를 차례로 넣도록 고쳤다.

**`t6-01` tweak ③ 을 교체했다.** 처음에는 "useEffect 를 지우고 fetch 를 컴포넌트 본문에 두면 요청이 여러 번 나간다" 로 썼는데, 이것은 **끝나지 않는 요청 루프**다. 본문 fetch → `setState` → 재렌더 → 본문 fetch 가 무한히 돈다. F-004(콘솔 로그 상한) 방침과 정면으로 부딪히고, `t4-12`·`t4-13` 에서 "배열 없음 + setState 조합" 을 뺀 이유와 같다. 주소를 `/api/nope` 로 바꿔 `t5-08` 의 `Unexpected token '<'` 를 다시 만나게 하는 것으로 바꿨다. 요청 1건이고, 에러 갈래가 없어 로딩에 갇히는 것을 보여 다음 레슨을 예고한다.

```
⑤ useFetch 로 뺀 뒤                             마지막 화면: 코스 4개
```

**경쟁 조건은 렌더를 나눠야 재현된다.** 처음에는 `root.render(A)` 와 `root.render(B)` 를 연달아 불렀는데 **첫 효과가 아예 돌지 않았다.** React 가 두 렌더를 하나로 합쳐 첫 커밋이 없었기 때문이다. 요청이 하나만 나가 경쟁이 성립하지 않았다.

```
합쳐진 경우   도착 · query = 리액트 심 · 1개        ← '리' 요청이 아예 없다
```

**`MessageChannel` 양보 세 번**을 사이에 넣으면 첫 커밋과 효과가 끝난 뒤 둘째 렌더가 간다. 이 양보는 **타이머가 아니라서 배경 탭 스로틀을 받지 않는다**(`validator.js` 의 `settle` 이 같은 이유로 쓴다). 그렇게 하니 재현됐다.

```
정리 없음   요청: 리 → 리액트 심 · 도착: 리액트 심(1개) → 리(2개) · 화면 = 2개
정리 있음   요청: 리 → 리액트 심 · 반영: 리액트 심(1개) · 버림: 리 · 화면 = 1개
```

무대의 지연 규칙은 **검색어가 한 글자면 400ms, 그보다 길면 40ms** 다. 짧은 검색어가 더 오래 걸리는 것은 실제 서버에서도 흔하다. 이 규칙 덕에 "먼저 보낸 것이 나중에 도착" 이 결정적으로 만들어진다.

**재요청 화면을 검사하려면 로딩이 다시 나타나야 한다.** 효과 맨 위에서 `setFound(null)` 을 부르지 않으면 새 검색 중에도 옛 결과가 남아 있어, 검사기가 "새 요청이 시작됐다" 는 시점을 알 수 없다. 레슨에서 이 줄은 사용자 경험을 위한 것이기도 하고 검사를 가능하게 하는 것이기도 하다. `t6-04` read 에 그 이유를 적었다.

**`key` 를 쓰지 않는다.** `t6-02`·`t6-03` 의 검사 하네스는 `key={url}` 로 다시 마운트시켰지만, `t6-04` 는 **의존성 배열이 동작하는지를 검사하는 레슨**이라 다시 마운트하면 의미가 없다. 배열이 `[]` 여도 통과해 버린다. 그래서 `key` 없이 같은 컴포넌트를 다시 렌더한다.

### T6 묶음 C 실측 — `env` 의 submit 무대 장치 (2026-08-21)

```
② type="button" 클릭          제출 없음 (onClick 만)
```


`dom` assert 는 액션 뒤 `settle` 두 번에 읽는데 응답은 300ms 뒤에 온다. 그래서 **중간 상태와 최종 상태를 나눠 검사하도록** 바꿨다 — `dom` 으로 누른 직후의 '보내는 중…' 과 버튼 잠김을 보고, `value` 로 `settled()` 를 불러 끝나기를 기다린 뒤 결과를 본다. 중간 상태를 검사하게 된 것이 오히려 이 레슨의 주제와 맞는다.

### T7 착수 전 실측 — 실행 프레임의 `this` (2026-08-21)

**실행 프레임은 sloppy mode 다.** 사용자 코드가 classic script 로 주입되므로 `'use strict'` 가 없다.

```
최상위 this === window       true
최상위 this === globalThis   true
함수 안 this (그냥 호출)      window        ← sloppy
typeof module / exports      undefined undefined
```

**호출 방식별 `this`**

```
① 그냥 부르면            window
② 메서드로 부르면         그 객체
③ 떼어 내어 부르면        window          ← 실무와 다르다. 아래 참조
④ call 로 넘기면          넘긴 객체
⑤ apply 로 넘기면         넘긴 객체
⑥ bind 한 뒤             고정됨 · 다시 call 해도 바뀌지 않는다
⑦ 화살표를 메서드로 두면   window (렉시컬)
⑧ new 로 부르면           새 인스턴스
⑨ new 없이 부르면         window 를 더럽힌다 (window.tag 가 생겼다)
```

**실무와 어긋나는 지점은 하나다.** 실무의 React 코드는 ES 모듈이고 모듈은 언제나 strict 다. strict 에서 ③은 `window` 가 아니라 **`undefined`** 다. "메서드를 떼어 내 넘겼더니 `Cannot read properties of undefined`" 가 실무에서 보는 증상인데, 이 프레임에서는 조용히 `window` 가 들어와 다른 증상이 난다.

**학습자가 직접 실무 조건을 만들 수 있다.** 코드 맨 위에 `'use strict'` 한 줄이면 된다.

```
'use strict' 안 · 그냥 부르면      undefined
'use strict' 안 · 떼어 내어 부르면  undefined
```

**`class` 본문은 언제나 strict 다.** 프레임이 sloppy 여도 그렇다.

```
class 메서드를 떼어 내어 부르면   TypeError: Cannot read properties of undefined (reading 'v')
```

그래서 **`class` 를 다루는 레슨(`t7-07`~`t7-09`)은 왜곡이 없다.** 함수와 객체를 다루는 앞쪽 레슨만 이 차이를 지문에서 밝히면 된다.

**프로토타입**

```
Object.getPrototypeOf(box) === Box.prototype              true
Object.getPrototypeOf(Box.prototype) === Object.prototype true
box.hasOwnProperty === Object.prototype.hasOwnProperty    true   ← 물려받은 것
class 게터 · 정적 메서드 · 인스턴스 메서드                  전부 정상
```

### T7 묶음 A 실측 (2026-08-21)

### T7 묶음 B 실측 (2026-08-21)

**`bind` · `call` · `apply`**

```
call                      안녕하세요, 리액트 입문입니다!     ← 인자를 낱개로, 즉시
apply                     반갑습니다, 리액트 입문입니다.     ← 인자를 배열로, 즉시

```

**부분 적용을 레슨에 넣었다.** 재현됐고, `bind` 만 그것을 할 수 있는 이유가 분명하기 때문이다 — `call`·`apply` 는 그 자리에서 부르고 끝나 기억해 둘 곳이 없지만 `bind` 는 새 함수를 만들어 두므로 `this` 도 인자도 함께 넣어 둘 수 있다. T1 의 클로저와 같은 성질이라 `t7-04` read 에 그렇게 적었다. `partial.length` 가 2에서 1로 줄어든 것도 tweak 에 넣었다 — 미리 넣은 만큼 받을 인자가 준 것이 숫자로 드러난다.

**프로토타입 체인**

```

hasOwnProperty 는 동작      true · 출처 Object.prototype  (같은 함수)
toString 도 마찬가지        [object Object]
한 단계 위                  Object.prototype
그 위                       null                          ← 체인의 끝
__proto__                  getPrototypeOf 와 같은 것
배열                        Array.prototype → Object.prototype · map 은 거기

가리기                      아래가 이기고 위는 그대로 남는다
```

**`__proto__` 와 `Object.getPrototypeOf` 를 둘 다 보여 주되 쓰는 쪽을 밝혔다.** 코드에는 `getPrototypeOf` 를 쓰고 `__proto__` 는 남의 코드와 개발자 도구에서 읽을 줄만 알면 된다고 적었다. 이 트랙의 목적이 읽기라는 것과 맞는다.

**`new` 가 하는 일 네 가지 — 전부 관측했다.**

```
① 안에서 this 가 빈 객체인가                    true
② this 의 프로토타입이 Course.prototype 인가     true
③ 본문 실행                                    name·hours 가 새 객체에 담김

```

**`new` 없이 부르면** — `t7-01` 실측 ⑨의 회수 자리다.

```

```

오류가 나지 않는다는 것이 이 사고의 성격이다. `t7-06` write 에서 `this instanceof Course` 로 스스로 막는 옛 라이브러리 방식까지 쓰게 했다. `class` 가 이것을 어떻게 막는지는 `t7-07` 이다.

### T7 묶음 C 실측 — `class` (2026-08-21)


### F-014 파비콘 SVG 가 파싱되지 않았다 — **처리 완료 (2026-08-21)**

- **처리 상태** — **처리 완료** (커밋 `ca0d9c6`).
- **증상** — 배포된 `favicon.svg` 를 브라우저에서 직접 열면 XML 파싱 오류가 난다. 파일 전체가 그려지지 않는다.

```
error on line 5 at column 19: Comment must not contain '--' (double-hyphen)
error on line 6 at column 41: Comment must not contain '--' (double-hyphen)
```

- **원인** — XML 주석은 내용에 붙임표 두 개를 담을 수 없다. 파비콘이 커스텀 프로퍼티를 참조할 수 없는 이유를 주석에 적으면서 토큰 이름을 `--c-clay-600` 처럼 **그대로 옮겨 적었다.** 그 두 글자가 주석을 끝내는 문자열로 해석돼 문서 전체가 깨졌다.
- **처리** — 토큰 이름을 `c-clay-600 토큰` 으로 적었다. 설명 내용은 그대로 두고 표기만 바꿨으며, 왜 그렇게 적는지도 주석에 남겼다.
- **고친 뒤 확인** — 브라우저로 **직접 열어** 확인했다.

```
직접 열기   HTTP 200 · image/svg+xml · 루트 요소 svg · 파싱 오류 없음
            도형 3개 · 화면에 그려짐
주석 검사   주석 내용의 붙임표 두 개 0건 · 주석 밖 0건
앱에서      favicon.svg 200 image/svg+xml · 콘솔 에러 0건
Lighthouse  읽기 100/100/100/100 · 쓰기(스냅샷) 100/100/100 — 유지
```

`favicon.svg` 를 직접 연 탭에서만 콘솔 에러 1건이 남는다. SVG 문서 자체에는 `<link rel="icon">` 이 없어 브라우저가 그 페이지의 파비콘으로 `/favicon.ico` 를 찾다 404 가 나는 것이다. **앱 페이지에서는 0건**이다.

- **왜 M7b 검증에서 걸리지 않았는가** — **파일을 만든 뒤 열어 보지 않았다.** M7b 에서 한 확인은 셋이었다.

| 한 것 | 통과했나 | 무엇을 못 봤나 |
|---|---|---|
| `curl -sI …/favicon.svg` | 200 · `image/svg+xml` | 서버가 준다는 것뿐. **내용이 유효한지는 보지 않는다** |
| 배포판 HTML 에 `<link rel="icon">` 이 있는지 | 있음 | 링크가 걸렸다는 것뿐 |
| Lighthouse 모범 사례 | 96 → 100 | **파비콘이 그려지는지는 Lighthouse 가 감사하지 않는다** |

세 번째가 특히 함정이었다. 점수가 오른 것은 맞다 — 링크가 걸려 브라우저가 `/favicon.ico` 를 더 찾지 않게 됐고 콘솔 에러가 사라졌기 때문이다. **그 점에서 96 → 100 은 유효한 측정이었다.** 다만 목표는 "점수 올리기" 가 아니라 "파비콘 달기" 였고, **그 목표는 달성되지 않았는데 지표만 달성됐다.** 지표가 목표를 대신 증명해 주지 않는다.

**규칙으로 남긴다 — 새로 만든 자산 파일은 만든 도구가 아니라 그것을 쓸 도구로 열어 본다.** SVG·이미지·JSON·HTML 모두 같다. `curl` 의 200 은 파일이 존재한다는 뜻이지 유효하다는 뜻이 아니다. 이번에는 브라우저로 열어 루트 요소와 도형 수와 그려진 크기까지 확인했다.

## M4 착수 전 실측 — 모듈과 경로 (2026-08-21)

브랜치 `feat/m4-module-runner`. `main` 에는 `v1.0-pre-m4` 태그를 붙여 두었다.

### 실행 프레임에서 ES 모듈이 되는가

```
origin = null · baseURI = 부모 문서 URL (계층 경로 있음)
A. <script type="module">        실행됨
C. 동적 import(blobUrl)          동작 · export 를 그대로 받는다 (double(21) = 42)
G. data: URL 모듈                동작
```

**모듈 자체는 문제가 아니다.** 막히는 것은 경로 해석 하나다.

### 상대 경로가 막히는 지점

`URL.createObjectURL` 이 opaque origin 에서 만드는 URL 은 **`blob:null/<uuid>`** 다. 계층 경로가 없다.

```
D. blob 모듈 안에서 './utils.js'
   TypeError: Failed to resolve module specifier "./utils.js".
              Invalid relative url or base scheme isn't hierarchic.
```

상대 지정자는 **참조자의 base URL 로 먼저 해석**되는데 `blob:null/…` 은 그 base 가 되지 못한다. import map 이 있어도 마찬가지다 — 해석이 먼저 실패하므로 맵을 찾아보는 단계까지 가지 않는다.

### 살아 있는 길 셋

파싱 시점에 `<script type="importmap">` 을 head 에 두고 잰 결과다.

| 방법 | 결과 | 학습자가 쓰는 코드 |
|---|---|---|
| ① import map + **bare 지정자** | **동작** (`import { bare } from 'utils'`) | `'utils'` — 실무의 `'./utils.js'` 와 다르다 |
| ② import map + **상대 경로** (blob 안) | **실패** — 위 D 와 같은 오류 | — |
| ③ **인라인 `<script type="module">` 의 상대 경로** | **동작** (문서 base 를 쓴다) | 진입 파일에만 해당 |
| ④ **지정자를 절대 blob URL 로 재작성** | **동작** (3파일 사슬 → 14) | `'./utils.js'` 그대로 — 실무와 같다 |

### ④ 를 더 재 봤다

```
⑤ 다이아몬드 의존 · 공통 모듈 본문 실행 횟수 = 1     ← blob URL 단위로 모듈 캐시가 정상 작동
⑥ 재작성 뒤 에러 위치 = at Module.go (blob:null/f3d61b2f-…:4:9)
⑦ 문법 오류 → SyntaxError: Unexpected token ';'      ← 동적 import 의 거부로 온다. 줄 번호가 없다
⑧ 최상위 throw → import 가 거부됨 · '최상위에서 던짐'
```

**⑥ 이 중요하다.** 지정자만 같은 줄에서 길어지므로 **줄 번호가 그대로 유지된다.** 그리고 파일마다 blob 이 따로이므로 **줄 번호가 이미 파일 기준**이다 — 지금의 `lineno - offsetOf(head)` 같은 오프셋 보정이 모듈 경로에서는 아예 필요 없다. 대신 필요한 것은 `blob:null/<uuid>` → 파일 이름 표다.

**⑦ 은 구멍이다.** 문법 오류가 거부 메시지로만 오고 줄 번호가 없다. 지금 classic 경로는 `window.onerror` 의 `lineno` 로 줄을 짚어 준다.

### 진입 식별자

```
I. export 한 것          typeof mod.doubleAll === 'function' · window.doubleAll 은 undefined
J. export 를 빠뜨리면     모듈 키 = [] · 오류 없음 · window 에도 없음
```

**J 가 오진을 부른다.** 지금 검사기는 이 상황에서 "함수를 찾을 수 없습니다" 를 낸다. 학습자는 함수 이름을 틀렸다고 읽지만 실제 원인은 `export` 누락이다.

### M4 실측 2 — 오류 위치와 Babel 비용 (2026-08-22)

**문법 오류에 줄 번호를 붙이는 데 Babel 이 필요 없다.** 붙이는 방법이 갈랐다.

```
① 동적 import(blobUrl)              SyntaxError: Unexpected token ';' · 줄 정보 없음
② <script type="module" src=blob>   window.onerror → 3행 18열          ← 정확
③ classic <script src=blob>         window.onerror → 3행 11열
④ new Function(src)                 줄 번호가 엉뚱하다 (:44:9 — 래퍼 기준)
⑤ Babel 콜드 로드                    650ms · 위치 (3:17) · 두 번째 import 0ms
```

앞선 실측에서 동적 `import()` 에 줄 번호가 없던 것은 **붙이는 방법의 문제**였다. 같은 blob 을 `<script type="module" src=…>` 로 붙이면 `window.onerror` 가 파일 기준 줄과 열을 준다. `src` 가 그 파일의 blob URL 이므로 **어느 파일인지도 함께 온다.**

**의존 파일까지 정확하다.** 진입 파일만이 아니다.

```
① 의존 파일 문법 오류      utils.js 3행 18열 · Uncaught SyntaxError: Unexpected token ';'
② 의존 파일 최상위 throw   utils.js 3행  7열 · Uncaught Error: 세 번째 줄에서 던짐
③ 진입 파일 실행 에러      main.js  3행  6열 · Uncaught TypeError: Cannot read properties of null
```

**부트 모듈로 네임스페이스를 건네받을 수 있다.**

```
④ import * as ns from '<진입>'; window.__entry = ns;
   → export 키 ["doubleAll"] · doubleAll([1,2]) = [2,4]
⑤ 그 경로에서 의존 파일이 깨지면
   → utils.js 1행 18열로 오류가 오고 window.__entry 는 undefined 로 남는다
```

**따라서 Babel 을 T8 에서 새로 받지 않는다.** 650ms 를 내고 얻을 것이 없다. `<script type="module">` 로 붙이는 것만으로 파일·줄·열이 전부 나온다. 줄 번호를 포기하는 선택지도 쓸 필요가 없다.

**순환 의존은 이번 측정으로 판정하지 못했다.** 탐침을 잘못 만들어(자리표시자를 남겨 둔 채 blob 을 굳혔다) 실패로 나왔다. ES 모듈이 순환을 지원하는 것과 별개로 이 프레임에서의 거동은 **미측정**이다. T8 이 순환 의존을 가르치지 않으므로 지금은 막지도 열지도 않는다.

### M4 실측 3 — 실패 마감 시점과 blob 의 출처 (2026-08-22)

**모듈 스크립트의 `load` 는 성공 신호가 아니다. 마감 신호다.**

```
① 진입 파일 문법 오류    load  3ms · onerror 1:11 SyntaxError
② 의존 파일 문법 오류    load  2ms · onerror utils.js 1:18 SyntaxError
③ 최상위 throw          load  2ms · onerror utils.js 1:7  Error: 터짐
④ 정상                  load  2ms · onerror 0건
⑤ 없는 이름을 import     load  2ms · onerror main.js 1:10 SyntaxError: The requested module …
⑥ 부모가 만든 blob       error 5ms · onerror 0건
⑦ window load = 4ms (파서 삽입 모듈이 깨진 문서에서도 온다)
```

문법 오류든 최상위 throw 든 요소의 `load` 가 **2~3ms 안에** 온다. 요소의 `error` 는
파싱 실패에는 오지 않고 **가져오기 실패에만** 온다(⑥). 그래서 판정은 이렇게 갈린다.

- `load` 가 왔는데 부트가 `__startAsserts` 를 부르지 않았다 → **모듈 실패**
- `error` 가 왔다 → 파일을 가져오지 못했다

**워치독에 기대지 않아도 된다.** 3초를 기다릴 이유가 없어졌다. 실패도 2~3ms 안에 마감한다.

**⑥ 이 설계를 하나 바꾼다.** opaque origin 프레임은 부모 출처의 blob URL 을 읽지 못한다.
따라서 **blob 은 프레임 안에서 만들어야 한다.** 프레임이 문서로 들어오기 전에는 blob URL 이
없으므로 모듈 스크립트를 **파서가 삽입할 수 없다.** 프레임 안 classic 부트스트랩이 동적으로
붙인다. 앞선 실측이 전부 동적 삽입이었으므로 측정 결과는 그대로 유효하다.

**⑤ 가 오류 보고에 한 갈래를 더한다.** 학습자가 없는 이름을 `import` 하면 실행 전
링크 단계에서 `SyntaxError: The requested module …` 로 끊긴다. export 누락(A~D)과 달리
`import` 쪽을 고쳐야 하는 경우다.

### F-016 안내(`#notice`)가 조건이 끝나도 사라지지 않는다

- **처리 상태** — **처리 완료.** 안내마다 사라지는 조건을 붙였다.
- **증상** — 좁은 폭에서 열었다가 넓히면 편집기가 떠 있는데도 "화면이 좁아 읽기 전용입니다" 가 남는다. 실측: 375px 에서 `t7-09[4]` 를 연 뒤 1280px 로 넓히면 `.cm-editor` 가 붙고 실행 버튼이 살아나는데 안내 문구는 그대로였다.
- **범위** — `v1.0-pre-m4` 부터. M4 와 무관하다.
- **원인** — 두 가지가 겹쳤다.

  ```js
  const shown = new Set();
  const notify = (message) => {
    if (shown.has(message)) return;
    shown.add(message);
    noticeEl.textContent = message;   // 지우는 경로가 없다
  };
  ```

  ① **지우는 경로가 아예 없었다.** 띄우기만 하고 걷지 않는다.
  ② `shown` 이 세션 내내 남아, 같은 안내가 나중에 **정말로** 필요해져도 다시 뜨지 않는다. 저장이 다시 실패해도 조용하다.

- **안내마다 수명이 다르다.** 한 규칙으로 묶을 수 없어 표로 정리했다.

  | 안내 | 뜨는 조건 | 사라지는 조건 |
  |---|---|---|
  | `readonly` 화면이 좁아 읽기 전용 | 폭 <768 이라 편집기를 만들지 않았다 | 편집기가 생기면 |
  | `fallback` CDN 폴백 | 편집기가 textarea 로 대체됐다 | 편집기가 사라지거나 CodeMirror 로 뜨면 |
  | `saveFailed` 저장 실패 | 저장이 실패했다 | 다음 저장이 성공하면 |
  | `codeChanged` 예제 코드가 바뀜 | 저장분이 지금 예제 코드와 다르다 | 되돌리기를 누르면 |
  | `discarded` 강제 종료 코드 버림 | 워치독이 끊어 저장분을 버렸다 | 학습자가 코드에 다시 손대면 |
  | `stale` 도구가 새 버전으로 바뀜 | 캐시된 `BUILD` 와 `version.json` 의 커밋이 다르다 | **사라지지 않는다.** 페이지를 다시 열기 전에는 사실이 바뀌지 않는다 |

  `stale` 을 뺀 다섯은 **단계를 옮기면** 사라진다. 앞 단계의 사정을 말하던 글이기 때문이다.

  `readOnly` 파일 안내는 `#notice` 가 아니라 탭 아래 `.file-tabs__note` 에 있다. 활성 파일이 바뀔 때마다 다시 계산되고 탭과 함께 사라지므로 이 결함에 해당하지 않는다.

- **고친 방법** — 문구 대신 **열쇠**로 다룬다. `notify(key)` 는 지금 떠 있는 것과 같은 열쇠면 넘어가고, `dismiss(key)` 는 **그 안내가 지금 떠 있을 때만** 지운다(다른 안내를 덮어 지우지 않는다). 편집기 상태가 바뀌는 지점은 `editorChanged(editable, mode)` 하나로 모았다. 단계 전환(`setContext`)에서 전부 비운다.
- **실측 확인** — 375px 열기 → 안내 뜸 / 1280px → `.cm-editor` 붙고 안내 **빈 문자열** / 500px → 안내 다시 뜸.

### M4 실측 4 — react+files 조합과 진짜 순환 (2026-08-22)

**A. Babel 을 `sourceType: 'module'` 로 돌려도 셋 다 지켜진다.**

```
① import 원문 유지    "import { Card } from './card.js';"
   export 원문 유지    "export function List({ items }) {"
   require 로 바뀌나    아니오
② retainLines         원본 8줄 → 변환 8줄 · JSX 는 7행 자리에서 그대로 변환
   문법 오류 위치       3:10 (정확)
③ 모듈 스코프의 UMD 전역 React = 진입 파일과 의존 파일 양쪽에서 보인다
```

`preset-react` 만 쓰고 `preset-env` 의 모듈 변환을 붙이지 않으므로 `import`/`export` 가 통과한다. 따라서 **`runtime: 'react'` + `files[]` 를 열 수 있다.** Babel 은 React 레슨에서 이미 받으므로 추가 비용이 없다.

**B. 진짜 순환은 blob URL 재작성 방식으로는 만들 수조차 없다.**

앞선 두 번의 순환 측정이 모두 틀렸다. blob 의 내용은 만드는 순간 굳고 URL 은 그전에 알 수 없다. 그래서 두 파일이 서로의 최종 URL 을 담는 것이 **원리적으로 불가능하다.** 앞선 탐침들은 순환처럼 보이는 사슬을 만들어 놓고 "순환이 된다/안 된다" 를 말하고 있었다.

**맨 지정자 + import map 으로 바꾸면 가능하다.** 이름은 blob 이 생기기 전에 이미 정해져 있기 때문이다.

```
① 실행 시점에 심은 import map = "HI" · 오류 없음
② 진짜 순환 (a ⇄ b, 진입은 a)
   b.js 가 최상위에서 a 를 읽으면 = ReferenceError: Cannot access 'a' before initialization
   a.js 가 본 것                  = { bAtTop: "B", readBLater: "A" }
   네임스페이스                    = ["a", "readA"]
   오류                           = 없음
```

**이것이 실제 ES 모듈의 거동이고 그대로 교재가 된다.** 나중에 부르는 함수로 읽으면 멀쩡하고, 최상위에서 즉시 읽으면 TDZ 에 걸린다. 우리 엔진의 정책이 아니라 언어의 성질이다.

**엔진을 바꾼다.** 지정자를 blob URL 로 재작성하는 대신 `'./이름'` 에서 `./` 만 떼고, 이름 → blob URL 의 import map 을 프레임 안에서 심는다. 부수 효과로 **위상 정렬이 필요 없어진다** — 이름이 먼저 정해지므로 순서가 의미를 잃는다. 순환 차단도 함께 없앤다.

### 회귀 하네스가 느린 이유 — 실측 (2026-08-22)

전수 회귀가 13분 넘게 걸려 어디에 쓰이는지 쟀다.

```
부팅 34ms · hidden=true
레슨      레슨 전환   단계 전환 합   실행 평균
t1-03        9ms         5ms          69ms
t2-06        7ms         5ms          52ms
t3-05        5ms         9ms        3,597ms
t4-05        8ms        11ms         117ms
t5-04        9ms        15ms       2,455ms
t6-03        9ms        15ms       9,986ms
t7-02       11ms         8ms          62ms
t8-01        7ms        10ms          57ms
t8-05        9ms         9ms         120ms
```

**전환은 이미 공짜다.** 레슨 전환 5~11ms, 한 레슨의 단계 전환을 다 합쳐 5~15ms. `showStep` 이 동기라서다. 실행 버튼이 살아나기를 기다린 것도 **0 tick** 이었다 — `applyPolicy` 가 `showStep` 안에서 동기로 돌아 편집기 마운트를 기다릴 필요가 없다.

**시간은 전부 실행에 있다.** 그리고 트랙마다 두 자릿수 차이가 난다.

- `t3-05` 의 3,597ms 는 Babel·React **첫 로드**다. 표본에서 T3 가 처음 React 를 쓰는 레슨이라 2회에 나눠 붙었다. 뒤따른 `t4-05` 는 117ms 다.
- `t5-04` 2,455ms · `t6-03` 9,986ms 는 **가짜 응답의 `setTimeout` 지연**이다. 하네스 탭이 `hidden` 이라 프레임 안 타이머가 **1000ms 로 조여진다**(F-001). 300ms 지연 셋이 3초가 된다.

**하네스의 대기 방식은 원인이 아니다.** 회전(MessageChannel)과 관찰(MutationObserver)을 같은 표본으로 비교했다.

```
(가) MessageChannel 회전  실행 8회 · 평균 5,964ms · 회전 647,939회
(나) MutationObserver     실행 8회 · 평균 5,975ms · 회전 196회
```

**시간은 같다(0.2% 차, 노이즈).** 회전이 타이머를 느리게 만들지도, 관찰이 빠르게 만들지도 않는다. 다만 회전은 64만 번 도는 동안 메인 스레드를 태우므로 관찰로 바꿨다. **속도가 아니라 위생 문제였다.**

CLAUDE.md 의 "하네스에서 `setTimeout` 금지" 는 지켜지고 있었다 — 하네스는 `setTimeout` 으로 기다리지 않는다. 조여지는 것은 **검사 대상인 앱 쪽 타이머**이고, 그것은 하네스가 고칠 수 없다.

**그래서 줄인 것은 범위다.** 두 하네스에 `?track=` 을 달았다.

### F-017 배경 탭에서 `dom` assert 가 로딩 화면을 읽는다

- **처리 상태** — **관측만 남긴다.** 처리 방향은 정하지 않았다.
- **증상** — `t6-03[3]`(갈래를 정하는 줄 채우기)을 정답 코드로 실행하면 **2 / 6 통과** 로 끝난다. 실패한 넷은 전부 같은 모양이다.

  ```
  실패 — 목록이 있으면 목록 | 기대: 코스 3개… | 실제: 불러오는 중…
  실패 — 코스 줄이 세 개   | 기대: 3          | 실제: 0
  ```

  통과하는 둘은 **에러 갈래**다(서버가 거절 / 닿지 못함). 성공 응답을 기다리는 검사만 실패한다.

- **원인** — 배경 탭의 타이머 조임이다. 실측:

  ```
  setTimeout(100) → 최상위 프레임    876 / 1000 / 1002 / 998 ms
  setTimeout(100) → 자식 프레임      980 / 999 / 1000 / 1000 ms
  ```

  가짜 응답이 `setTimeout` 으로 지연을 흉내 내는데 그것이 1000ms 로 조여진다. `dom` assert 는 정해진 만큼만 기다렸다가 DOM 을 읽으므로 아직 로딩 화면이다.

- **F-001 계열이지만 증상이 다르다.** F-001 은 ping 이 늦어 **워치독이 멀쩡한 프레임을 죽이는** 오탐이었고, 그쪽은 `document.hidden` 가드로 막았다. 이쪽은 검사가 **너무 이른 화면을 읽는** 것이라 가드가 걸리는 자리가 없다.

- **M4 와 무관한 기존 조건이다.** 지금 배포된 `main` 이 아니라 **M4 이전 판**(커밋 `7ae61500`)에서도 그대로 재현된다.

  ```
  preview(Pages, M4 포함)   2/6 · 16995ms
  로컬 직접 (M4 포함)        2/6 · 15553ms
  main 배포 (M4 이전 판)     2/6 · 16995ms   ← 대조군
  ```

- **하네스 안에서는 통과한다.** 같은 단계를 회귀 하네스로 돌리면 **6 / 6 · 10134ms** 다. 하네스는 앱을 iframe 에 담고 `#status` 가 마감될 때까지 기다리므로 검사에 시간이 더 주어진다. 그래서 113레슨 전수 회귀는 이 단계를 통과로 기록한다.

- **탭이 실제로 보이는 상태는 측정하지 못했다.** 스크린샷으로 창을 앞에 올린 직후에도 `setTimeout(100)` 이 **1566ms** 로 나왔다. 이 도구로는 조여지지 않은 측정을 얻을 수 없다.

- **그래서 실제 학습자에게 문제가 되는지는 미측정이다.** 보이는 탭에서 300ms 지연이 300ms 로 도는지 확인하지 못했다. 확인 없이 "학습자에게는 괜찮다" 고 쓰지 않는다.
